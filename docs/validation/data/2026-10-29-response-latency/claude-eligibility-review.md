## 結論

この6行のガードによる、正しさ・所有権・キャンセルに関する重大な退行は見当たりません。具体的なランタイムバグもありません。

## 確認した点

- **所有権 / drain**: ガードは `preparation` Task を生成する前に `return` します。このため、cancel や join が必要な子タスクは存在しません。`withTaskCancellationHandler` の外側で抜けても、取り残されるタスクはありません。
- **キャンセル**: `normalizedInput` の末尾に `Task.checkCancellation()` があり、ガードの直前でキャンセルが確認されます。その後の `channel.next()` は、親がキャンセルされると channel が close されるので、`nil` を返すか throw します。そのため、無期限に待ち続けることはありません。catch 経路の明示的な `checkCancellation()` が無い点は差異ですが、実害はありません。
- **確定入力の扱い**: `next()` は後続の candidate をスキップします。`prepare(confirmed)` は通常経路なので、再正規化・2000 検証・確定前に再生しない、という既存の不変条件をそのまま継承します。candidate が長くて confirmed が短い場合も、通常経路になるだけで正しく動作します。
- **長さの単位**: `spoken.count` は書記素クラスタ数です。2000 検証と同じ単位なので一貫しています。trim 後の値で判定している点も、再利用判定 (`actual == spoken`) と整合しています。

## 軽微 / 情報

- **重大度: 低(計測のみ)**: ガード経路では `used == false` のまま抜けるため、`defer` が `.preparationDiscarded` を記録します。実際には投機合成を開始していないのに「破棄」として計上されます。既存の正規化失敗経路と同じ挙動なので一貫性はありますが、reuse 率や discard 率を分析するときに「長さで除外」と「不一致で破棄」が区別できません。実機や real-cloud の reuse 評価で数字を解釈する際は、この点に注意してください。
- **重大度: 極低(性能)**: 長い candidate の正規化コストは無駄になり、confirmed 側で再度正規化されます。正しさには影響しません。
