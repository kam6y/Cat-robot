## P1（Important）: 英字に付いた `+` が「タス」（足す）と読まれる
- **再現**（`findings.out`）
  - `Disney+を見よう。` → `ディズニータスヲミヨー。`
  - `Apple TV+` → `アップル テレビタス`
  - `Nintendo Switch+` → `…スイッチタス`
  - `成績はA+だよ。` → `セーセキワエイタスダヨ。`
  - `A+B` → `エイタスビー`
  - `x+1` → `エックスタスイチ`
  - `g++` → `ジータスタス`
  - `i++` → `アイタスタス`
  - `C++`、`c++`、`Ｃ＋＋` と、前に英字がない `+ボタン`・`1+2` は正しく読める。
- **原因**
  - `lib.rs:28-29` の `IDENTIFIERS` は `[A-Za-z_][A-Za-z0-9_+]*` で、`+` まで識別子に取り込む。
  - そのため `verbalize_plus`（`lib.rs:224-234`）は、`Disney+` の `+` を「プラス」に変えない。
  - その結果、NJD は `("＋","タス",2)` を選ぶ。
- **影響**: spec の規則 3（単独の `+` は「プラス」）にも、利用者の元の不満（`+` の誤読）にも反する。サービス名・成績・式など、日常でよく使う書き方が対象になる。
- **修正案**（どちらでも良い）
  - (a) 最小の修正: `IDENTIFIERS` を `(?i:c\+\+)|[A-Za-z_][A-Za-z0-9_]*` に変える。
  - (b) 汎用の修正: 識別子の末尾に `+` が付いているときは、識別子全体を `text_to_njd` で引く。1 ノードで、かつ mora が 1 以上の既知語なら、そのまま残す。それ以外は `+` を「プラス」にする。(b) は、`lib.rs:126-138` の単語の再照会と同じ手法である。
- **修正案を入れて確認した結果**（コピーに (a) と P2 の修正を入れて実行。`patched.out`）
  - crate 自身のテストは、変更なしで 14 件すべて合格した（実辞書の 10 件と C ABI の 4 件）。`tests/pronunciation.rs:50` の `zzqx+identifier`、:82-97 の区切りの完全一致、:145-151 の桁区切りを含む。
  - 出力
    - `Disney+を見よう。` → `ディズニープラスヲミヨー。`
    - `成績はA+だよ。` → `セーセキワエイプラスダヨ。`
    - `x+1` → `エックスプラスイチ`
    - `g++` → `ジープラスプラス`
    - `A+B` → `エイプラスビー`
    - `Google+` → `グーグルプラス`
    - `YouTube+` → `ユーチューブプラス`
    - `C++`・`c++`・`Ｃ＋＋` は今までどおり。
  - 未知語の保護は変わらない。
    - `zzqx+identifier`、`前foo+bar後`、`a+youtube@example.test` は原文のまま残る。
    - `Paramount+` は Paramount が辞書にないので、`+` を含めて原文のまま残る。
  - 汎用の (b) は実行していない。
- **追加したいテスト**: `Disney+`、`A+`、`x+1`、`g++` がそれぞれ上の出力になること。値は修正したコピーで実際に出たもの。

## P2（Important/中）: よく使う記号が 1 つ混ざると、区間全体が原文に戻り、`+`・YouTube・数字の補正が効かない
- **再現**
  - 区間全体が原文のまま返るもの
    - `+ボタンを押してね♪`
    - `+ボタンを押してね〜`
    - `1+2=3`
    - `YouTubeを見よう…`
    - `YouTube・Netflixを見る`
    - `+ボタン・−ボタン`
    - `3〜5個`
    - `にゃ〜`
  - このとき Supertonic には元の `+` がそのまま届くので、元の誤読がそのまま残る。
  - 対照: `+ボタンを押してね。` は正しく `プラスボタンヲオシテネ。` になる。
- **原因**
  - NJD は `〜`・`…`・`：` を pron `、`（mora 0）に、`♪` を pron 空（mora 0）にする。`＝` も mora 0 である。
  - `lib.rs:140-149` の mora 0 の検査に当たると、区間全体を原文に戻す。
  - 区切り文字の一覧（`is_separator`、`lib.rs:185-222`）には、これらの記号が入っていない。
- **影響**
  - 以前と比べて悪くなる（退行）わけではない。ただ、補正が黙って効かない文が日常的に出る。
  - `ConversationInstructions.swift:9` は絵文字と Markdown を禁じているが、`〜`・`…`・`♪`・`・`・`=` は禁じていない。猫の口調（「にゃ〜」「そうだね〜」）では特に出やすい。
- **修正案**
  - 次の文字を区切り文字に足す。記号は原文のまま残り、前後の区間は変換される。
    - `…` `‥` `・` `･` `〜` `～` `♪` `♫` `＝` `=` `※` `→` `←` `☆` `★` `♡` `♥`
    - 絵文字（Extended_Pictographic）
  - 代わりに、mora 0 のノードの位置で区間を分ける方法もあるが、NFKC による位置のずれを扱う必要があり、複雑になる。
  - 副作用: `3〜5個` は `サン〜ゴコ` になる。この `〜` を Supertonic がどう読むかは未確認。必要なら、数字に挟まれた `〜` を「カラ」にする小さな規則を足す（任意）。
- **修正案を入れて確認した結果**（同じコピーで実行。テストは 14 件すべて合格）
  - `+ボタンを押してね♪` → `プラスボタンヲオシテネ♪`
  - `+ボタンを押してね〜` → `プラスボタンヲオシテネ〜`
  - `1+2=3` → `イチプラスニ=サン`
  - `YouTubeを見よう…` → `ユーチューブヲミヨー…`
  - `YouTube・Netflixを見る` → `ユーチューブ・ネットフリックスヲミル`
  - `猫・犬` → `ネコ・イヌ`
  - `にゃ〜` → `ニャ〜`
  - `3〜5個` → `サン〜ゴコ`
  - `+ボタン・−ボタン` → `プラスボタン・−ボタン`（`−` を含む区間は原文のまま残る）
  - 修正後も走査で、黙って消えた文字は 0、エラーも 0 だった（`scan-patched.out`）。
- **追加したいテスト**: 上の出力（実際に出た値）。

## P3: 実用文で見えた読みと、聴いて確かめる必要があること（ブロッカーではない）
- **良好**（`practical.out`）
  - 助数詞と数: `8個`→ハッコ、`10分`→ジュップン、`20歳`→ニジュッサイ、`4日`→ヨッカ、`1人`→ヒトリ、`50%`→ゴジュッパーセント、`1,000円`→センエン、`3.14`
  - 日付: `2026年10月29日`
  - 普段の会話: `早く寝た方がいいよ`→ホー、`辛くない？`→カラクナイ
  - 英語名: `Netflix`、`Claude`、`Wi-Fi`、`iPad`、`Apple Watch`、`OK`、`AI`
- **誤読**
  - `辛いカレーが好き` → `ツライカレー…`（カライが正しい）
  - 文頭の `方がいい` → `カタガイイ`
  - `今日は25℃だよ` → `…ニジューゴドシーダヨ`（ニジューゴドが正しい）
  - `7:30に起こしてね` → `ナナ:サンジュー…`、`10:30` → `ジュー:サンジュー`
- **原文のまま残るもの**（変更前と同じ）: `ChatGPT`、`GitHub`、`AirPods`、`USB-C`、`C#`、`1/2`、電話番号
- **置き換えによる新しいリスク**
  - 今回はすべて置き換えるので、漢字の読みは jpreprocess の選択に固定される。以前は Supertonic が漢字を自分で読んでいた。
  - 実機の比較 4 文（+、YouTube、数、挨拶）は改善を見る例だけで、悪くなっていないかは測れない。
  - 提案: 同音異義の文を 3〜4 文、旧（原文）と新（カナ）で聴き比べに加える。例: `辛いカレー`、`今日は25℃`、`7:30`、`日本`（→ニッポン）。
- **仮説**（聴くまで未確定）
  - を → `ヲ`、長音の `ー`（キョーワ・セーセキ・ミヨー）を Supertonic がどう読むかは不明である。
  - 既存のサンプル `YouTubeを見よう。` で「wo」に聞こえたら、変換後に `ヲ`→`オ` へ置き換えるのが安上がりである。発音に忠実なカナなので意味は変わらない。
- **任意の小さな規則**
  - `℃` → `度`
  - `\d{1,2}:\d{2}` → 時・分（比率や得点の `2:1` と区別が要るので慎重に）

## P4（運用と軽い指摘）
- **辞書は mmap ではなく、ヒープにコピーされる**
  - 経路: `load_fs_dictionary` → lindera-dictionary 3.0.7 の `loader.rs:45-46` → `dictionary.rs:83-84` の `load_from_path_with_options(path, false)`。
  - 約 80MB（`dict.da` 33MB、`dict.words` 32MB など）が、アプリが動いている間ずっと、解放されないヒープに乗る。
  - mmap feature は有効になっている（`cargo tree -e features -i memmap2` で、lindera-dictionary の default feature から有効と確認）。
  - 実機での有効な計測はまだない。validation と ledger によると、最初の計測値（0.000176 秒、増分 0）は採用しないことになっている。
  - 実機で、メモリ使用量の増分がほぼ 80MB か、冷えた状態での初回ロードが目立つ場合は、`Dictionary::load_from_path_with_options(path, true)` で読む案を検討してほしい。mmap した読み取り専用ページは OS が必要に応じて捨てられる。API の互換は要確認である。
  - 補足: Rust のメモリ確保失敗は catch_unwind では捕まらず abort になる。ロード中のメモリ不足は、エラーではなくクラッシュになる。
- **Supertonic の indexer に `ヱ`（U+30F1）がない**
  - NFKD の後でも、`SupertonicEngine.swift:59-60` が受け付けない。
  - 単独の仮名・CJK 文字を走査したところ、`ヱ` を出すのは `ゑ`→`ヱ` だけだった。
  - `ゑ` も indexer にないので、退行ではない。`ヱ`→`エ`、`ヰ`→`イ` に置き換えると読めるようになる（任意）。
- **URL の保護**: `https://example.comを見てね` は、URL の後ろの日本語まで保護されて、原文のまま残る（`lib.rs:23`）。旧処理から引き継いだ挙動である（軽微）。
- **spec の文言の食い違い**
  - 規則 5 は「不正な出力 → その区間を原文に戻す」と書いている。
  - 規則 6 と FFI の節、実装（`lib.rs:161-167`）は音声エラーにしている。
  - ユーザーの判断（変換エラーは音声エラー）に合わせて、規則 5 の文言を直せばよい。
  - 走査では、この経路に入る入力は 1 つも見つからなかった。

## 問題なしと判断した点（根拠）
- **未知の文字が消えないこと**
  - 15,999 の code point を `猫{c}犬` に挟んで走査した。範囲は U+0000–2FFF、3000–30FF、FE00–FFFF、1F000–1FAFF、E0000–E007F。
  - 黙って消えた文字は 0、エラーも 0 だった。カナに変換された出力で、挟んだ文字の読みが抜けているものも 0 だった。
  - IVS（`葛\u{E0100}城`）は原文のまま残った。濁点の分離と結合も、既存テストどおりである。
- **2,000 文字の上限**: カナ 2,000 文字は、60 秒の PCM 上限（`SupertonicEngine.swift:64`）よりずっと長い。現実の文では、展開による新しい失敗は起きない。
- **停止**: `JapanesePronunciationService.swift:39,46` と `SupertonicSentenceSpeaker.swift:100` で、変換の後に停止を確かめている。停止後に合成・再生しないことの RED から GREEN は、codex の記録（ledger と validation）による。私は実行していない。冷えた状態の辞書ロードは同期処理で中断できないが、spec が許容している。
- **失敗の固定**
  - 一度失敗すると、その状態を保持する（`JapanesePronunciationService.swift:30-33`）。準備時の失敗は、`SupertonicErrorMapper.swift:7` で `speechSynthesisFailed` になる。
  - ユーザーの「旧処理へ戻さない」に合っている。その結果、再起動するまで返事は毎回音声エラーになる。これは了承済みの影響である。
- **FFI**
  - 失敗時に出力を null にしている。
  - 結果の文字列は、Swift がコピーしてから `defer` で解放している（`:72-75`）。
  - NUL と長さの検査は、Swift 側と Rust 側の両方にある。
  - `panic = "unwind"` と `catch_unwind` を使っている。
  - ハンドルへのアクセスは actor が直列化している。
  - 問題はない。

## 追記: device-host-fix.diff の限定確認（読み取り専用）
結論: 問題はなかった。通常起動と Release の振る舞いは変わらない。

- **分岐の範囲**（`CatRobotApp.swift`）
  - 空のホスト（`Color.clear`）になるのは、`#if DEBUG` で、かつ `SUPER_INTEGRATION_TESTS == "1"` のときだけ。
  - それ以外と Release（`#else`）は、今までどおり `.live()` で AppRootView を作る。
  - 通常の Simulator の全体テストは、この環境変数を設定しないので、影響を受けない。
- **環境変数の渡り方**
  - `run_supertonic_integration_device_test.sh:38` は、xctestrun の TestTarget の `EnvironmentVariables` に設定し、`OnlyTestIdentifiers` で専用テストだけを実行する。
  - 専用 scheme でも、変数は TestAction の中（`:39-79`）に置かれ、LaunchAction には入っていない。
  - アプリの中で実行するテストなので、この環境変数はアプリ側にも渡る。
  - テスト側は `#if targetEnvironment(simulator) || !DEBUG` でスキップする（`SupertonicIntegrationDeviceTests.swift:17`）。アプリ側の `#if DEBUG` と条件がそろっている。
- **計測が正しくなる理由**
  - 空のホストでは、AppRootView・ConversationAppCoordinator・speaker の prepare が作られない。そのため、`JapanesePronunciationService.shared` を最初に準備するのはテスト本体になり、初回ロードの計測が意味を持つ。
  - 音声セッションも、テストだけが `setCategory` と `setActive` を持つ（`:33-36`）。
  - 再生の assertion は消されていない。
- **画面の自動ロック**
  - 元の値を保存し、テスト関数の中の `defer` で元に戻している（`:26-28`）。setUp の中ではないので、テスト中ずっと効く。
  - クラスは `@MainActor` なので、UIApplication に触っても問題ない。
  - 途中でクラッシュしても、この設定はプロセスごとなので後に残らない。
- **因果について**
  - AVAudioEngine の 561015905 が、通常画面との競合で起きたというのは、ログに基づく仮説である。
  - この差分だけを入れて同じ実機の段階を再実行し、成功すれば、その原因を切り分けた証拠になる。
  - 現時点では未確認である。
