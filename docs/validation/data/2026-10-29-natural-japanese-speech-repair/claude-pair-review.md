## Important（実装前に決めたい）

### I1. 対象は「Latin 文字を1つ以上含む run」に限定する
- regex に digits/plus を入れると `3`・`25`・`1+2`・`7:30` の数字だけの run も対象になり、convert_run が NJD で `サン` 等に読む → RED の「3人で25個を分けるよ。」がそのまま壊れる。
- 数字・`+` だけの run は隙間扱い（`+`→プラス、数字原文）。`1+2=3` → `1プラス2=3`（既存期待値 `イチプラスニ=サン` は更新）。
- Latin を含む run 内の数字（`iPhone15`, `25cm`, `5G`）は convert_run が数字も読む（例 `アイフォーンジューゴ`、仮説）。spec の「数字は原文」と矛盾するので、どちらにするか決めて test で固定する。推奨: 語単位 all-or-nothing として辞書読みを許し、spec に例外として一行書く。

### I2. eligibility は NFKC 後判定ではなく、元文字のホワイトリストにする
- 対象内 NFKC は幅の畳み込み以外も変える。以下はどれも Script=Latin の文字。
  - `ﬁ`(Ll) → `fi`
  - `ª`(Lo) → `a`
  - `K`(U+212A, Lu) → `K`
  - `Ⅳ`(Nl) → `IV`
- 「NFKC 後 ASCII なら変換」にすると、これらが辞書読みに入る（例 `第Ⅳ章`）。`²` は Script=Common の No なので、class に `\p{N}` を入れない限り run に入らない。
- 推奨: run の各文字が ASCII `[A-Za-z0-9_+]` かその全角形（`Ａ-Ｚａ-ｚ０-９＿＋`）だけのときに限り対象。1文字でも他を含めば run 全体を原文保持。
- fold は 全角→ASCII だけ（alias 照合用）。辞書照合は既存の normalize_text_for_naist_jdic が全角化するので NFKC 自体が不要になる。
- これで `é`・`e+U+0301`・`zzqx+U+0301`・他 script 接尾が「同じ一規則」で保持される。

### I3. 他 script 接尾（質問への回答）
- 「部分書換えなし」を構成的に保証する最小形: 候補 run を「日本語 script 以外の語文字の最大連続」にし、I2 のホワイトリストで判定する。
  - 例: `(?:[\p{L}\p{N}_＿+＋&&[^\p{Han}\p{Hiragana}\p{Katakana}ーｰ]]\p{M}*)+`（Rust regex はクラスの `&&` に対応）
  - `ー`(U+30FC)・`ｰ`(U+FF70)・`ﾞ`(U+FF9E)・`ﾟ`(U+FF9F) は、どれも Script=Common の Lm なので、`\p{L}` に入ってしまう。除外しないと `YouTubeー` や `YouTubeﾞ` が一続きになり、補正が止まる。
  - 手書きの一覧を作る代わりに、Script_Extensions（`\p{scx=Hiragana}` / `\p{scx=Katakana}`）で除外する手もある。ただし、regex crate の scx がこの 4 文字をすべて含むかは確認していない。採るなら test で確かめてほしい。
  - I1 の「Latin 文字 1 つ以上」の規則があるので、これらが run に入っても誤変換は起きない。起きるのは補正が止まることだけ。
  - → `YouTubeα`, `ЯYouTube`, `valueΔ`, `caféYouTube` は run 全体を原文保持。
- 代替案: Latin-only regex にして、他 script を境界にする（`YouTubeα`→`ユーチューブα`）。これも可。その場合は仕様として test で固定する。
- 頻度はどちらも低い。規則が一つで説明しやすい前者を推奨する。

### I4. 結合記号は「基底文字の直後」だけ run に取り込む
- `(base \p{M}*)+` の形にする。`\p{M}` を run の独立メンバーにすると、`が` の `゙` や `❤️` の FE0F が run 先頭になり得る。
- I1 の「Latin 1文字以上必須」があれば変換は起きないが、境界の定義として崩れる。

### I5. 現 RED の一部は空振り
- `zzqxé` / `zzqx\u{0301}` / `zzqx+identifier` は stem が未知語なので、ASCII だけを拾う素朴な実装でも通る。部分変換されても未知語は原文に戻るので見えない。
- 既知 stem で固定する（すべて原文期待）:
  - `YouTubeé`, `YouTube\u{0301}`, `Ｂｌｕｅｔｏｏｔｈ\u{0301}`
  - `zzqx+YouTube`, `YouTube+zzqx`
  - `YouTubeα`（I3 で前者を採る場合）
- 13:18 の YouTubeé 案と同じ方向。

### I6. `Wi-Fi` / `don't` / `e-mail` の退行確認（仮説）
- `-` `'` `.` を run に入れない場合、`Wi` と `Fi` は別対象になる。
- 現 HEAD は ASCII `-` が SEPARATORS に無いので、`Wi-Fi` を一つの run として NJD に渡している。辞書に Ｗｉ－Ｆｉ があれば `ワイファイ` と読めていた可能性がある。
- 実辞書で現 HEAD の出力を一度確認する。
  - 読めていた場合: 「英数字に挟まれた `-` `'` `.` を run 内部に許す（全体で辞書照合し、失敗なら原文）」を足す。
  - 足さない場合: 退行として記録する。

### 確認して問題なし
- **文字クラスの書き方**: Rust regex のクラスでは、和集合が `&&` より強く結び付く。したがって `[\p{L}\p{N}_＿+＋&&[^…]]` は意図どおりになる。
- **`+` の扱い**:
  - `+` は語を開けず、語の内側と末尾だけで連結される（`Disney+`、`TV+`、`C++` は語として補正される）。
  - 隙間の `+` はプラスになる。
  - 数字だけの語は表記を保持し、`+` だけ置換する（`1+2`→`1プラス2`、`3.14` と `1,234` は原文）。
- **除外文字**: `ー` `ｰ` `ﾞ` `ﾟ` を除外しているので、`ｶﾞYouTube` は補正が効く。
- **幅の畳み込み**: 全角→ASCII だけに限定されている。`m²` と `Ⅳ` は対象外になって原文を保持する。
- **mora 0 の例外の削除**: numeric_separator の例外を外した影響は、小数を含む Latin 語（`v1.2` など）が原文に戻ることだけ。安全側の変化である。
- **Swift の上限境界**: 666×3+2=2000 で境界、667×3=2001 で上限超過になり、計算が合っている。

### 記録に正確に書いてほしい点（M3 の訂正）
- **私の記述の誤り**: M3 で「-1 のまま入る」と書いたのは誤り。`SupertonicEngine.swift:60` が ids<0 を `inferenceFailed` として拒否し、その文の合成が失敗する（codex の指摘どおり）。
- **C 方式で起きること**: 漢字を生で渡すので、indexer 外の漢字（JIS 第1水準 46 字、第2水準 1300 字）を含む文は、全体が合成失敗になる。
  - HEAD（全文カナ化）では、そうした漢字の多くがカナに変換されて読めていた。
  - 振る舞いの変化は「カナで読めた」→「その文の読み上げ失敗」で、jpreprocess 以前の legacy と同じ。
  - 会話でよく使う漢字の標本では、未収録は `饂` だけだった。
- **扱い**: 修正を止める問題ではない。validation の限界欄に、この挙動として記録する。
- **後続案**（別タスク）: indexer 外の漢字だけを読みに置き換える。

### Minor（仮説。私の I6 の提案に由来）
