## Defer: measured tradeoffs, not established performance defects

**E1/E2 session teardown and look restart — mechanism accepted; defer optimization, no Important defect established.** `ConversationCamera.swift:92-98,176-191` ends attention demand on classifying/thinking; returning to listening creates another physical session if no tracking/look owner kept it alive. `AppleFaceCaptureSource` configures and starts the session on its worker queue. The extra stop/rebuild operation count is real for devices without a ready tracking robot. For a look, the inherited 0.1-second look delay can follow attention teardown; the baseline already cold-started look, so the newly added cost is mainly teardown/serialization, not an assumed complete cold-start regression. No report measured duration, first-frame availability, power, or indicator behavior. Listening-only capture is an explicit design decision; retaining capture during classification/speaking changes its privacy/resource lifetime. Keep the existing policy for this change and record these as device-validation observations. A later optimization must preserve separate listening-entry invalidation, even if physical capture is retained.

**E3 retry on each listening entry — mechanism accepted; defer cooldown/backoff, no Important defect established.** `ConversationCamera.swift:97` clears the capture-failure latch at a new listening demand. Persistent unsupported configuration/interruption can therefore cause another failed startup per routed utterance. This is not an unbounded immediate retry loop: a new phase/listening edge or another explicit owner is required. Retry also allows recovery from transient failure without requiring a scene change. Suppressing it until external eligibility changes can leave attention unavailable after a transient failure has cleared. Measure the frequency/cost before changing this recovery policy; do not infer a paid-call or battery regression from operation counts alone.

## Reject or defer: duplicate validation/helpers

**R1/S4 timing-helper extraction — defer optional refactor (Minor maintainability only).** The checks overlap, but tracking allows completion up to `now + 1 µs`, attention requires `completedAt <= now` and `capturedAt >= attentionStartedAt`, and invalid input has different cache effects. A shared helper would need policy parameters or would silently change behavior in a previously untouched consumer. Keeping the short checks at their independent trust boundaries is defensible.

**S2/S3 removal of implied guards, R5 shared lease helper — reject as necessary changes.** Several guards are logically redundant under current invalidation invariants, and finite capture time is already checked by `CameraSnapshot.isFresh`. Explicit eligibility/ownership/live-authorization checks still make the public query's contract readable and robust to future writers. Removing them or introducing a helper for two repeated conditions saves little and provides no user benefit. Do not remove the live authorization check. This is a style choice, not a current bug.

**A2 phase predicate location/comment — defer (Minor documentation/organization).** `FaceCaptureEnvironment.permitsCapture` remains the common broad eligibility rule; listening-only attention is a narrower demand. A `requestsListeningAttention` property could express that distinction, but one local predicate is also appropriate. The type comment could mention attention, without moving logic or adding a new abstraction.

## Defer: test organization and unused generality

**R2/R4/S8 harness consolidation and domain-test placement — defer (Minor).** The camera harnesses overlap and pure policy tests can live in the domain suite. They deliberately start in different phases, and the new facing harness additionally holds tracking demand to test retention across listening boundaries. Consolidation must preserve that condition and the tracking-absent tests. Present layout is less tidy, not broken coverage.

**R3 app permission harness consolidation — reject an equivalent-substitution claim; defer any refactor.** Existing `FaceAppHarness` has tracking but no camera; the new test has camera but no tracking. These exercise different sides of `isAwaitingCameraPermission`. Simply changing tracking to disabled does not preserve the absent-collaborator path. Keep that distinction if sharing setup later.

**R6 broad removal of geometry cases — reject blanket deletion; retain cache-boundary behavior.** The camera tests do more than repeat geometry: several start from a valid facing observation, then feed malformed/unknown/multiple-face evidence and assert that cached attention is revoked. A pure geometry test does not prove that update behavior. One yaw-correction pass-through case and raw multi-face rejection are also integration contracts. Additional exact-boundary duplication can be trimmed later if desired.
