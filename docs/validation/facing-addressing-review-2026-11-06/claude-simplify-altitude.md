## Considered and ruled out

N1 closure seam vs protocol vs recognizer-path value: `ConversationDependencies` already uses closures for single sync queries (`now`, `clarificationDelay`, `noticeDelay`, `lifecycleCheckpoint`, `serviceTeardown`); protocols with Noop defaults are for multi-method collaborators with `ReplyTurnObserving` lifecycle; `isFacingScreen` is one query once per turn (:959); sampling during the utterance via recognizer/segmenter conflicts with the recorded route-time/0.4 s decision; phase stays `.listening` until routing (:982 `.classifying`, :1086 `.thinking`, both after :959), so route-time read is sound.
N2 cache/third demand in `ConversationCamera` vs separate attention object: `events()` cannot feed a second consumer (single `AsyncStream`, `bufferingNewest(1)` `FaceCapturePolicy.swift:105`; yields only while `trackingGeneration` set; re-stamps generation :251-255). Cache validity depends on camera-private state (`physicalGeneration` :249, `eligible`, `stopPhysical()` invalidation :187-192) and the demand must join `reconcile()` :177. A separate object would mirror nearly all camera state. Class doc :4 updated to "one physical capture, several demands".
N3 demand decided by coordinator vs camera: `setEnvironment` already receives `phase` on every change (`ConversationAppCoordinator.swift:102-103, :147`); a coordinator-side `setAttentionDemand` would repeat `== .listening` one layer up with an ordering dependency. Owners interact via one OR in `reconcile` :177; tracking keeps capture alive across turns and `attentionStartedAt` + `clearAttention` per edge stop pre-listening frames (test :138-153); look cold-starts in `.thinking` as before (only counts shift in `LookIntegrationTests.swift:69-81`). Resetting `captureFailed` on each listening edge (:97) follows the existing pattern where every new owner request clears the latch (`start(generation:)` :112, `captureSnapshot` :137), not a new special case; `FaceTrackingCoordinator`'s own latch (:143) is not cleared by camera recovery, already true for look. Recorded design decision: with tracking off each listening entry builds a new `AVCaptureSession` (`AppleFaceCaptureSource.swift:120-132`, `configure()` :187); a persistently failing device is re-configured every turn. Alternative: hold attention demand for the whole visible conversation, consult only while listening (continuous capture during thinking/speaking vs no churn). Not reported as a finding: routing impact should be small (≈3 fps for the utterance + 1.2 s silence window before the read).
N4 Bool input vs `EngagementWindow` vs richer evidence: facing cannot fold into `EngagementWindow` — (1) facing escapes the pending branch (`AddresseePolicy.swift:50`) but active engagement does not; (2) a facing accept re-arms (resets 300 s `armedAt`), follow-up only refreshes; (3) engagement is armed only after a successful reply (`ConversationViewModel.swift:1101-1105`); arming before routing would grant the 30 s bypass on reply failure. Richer enum unnecessary with one source. `guard isFacingScreen else { return .classify }` fall-through is equivalent but no shorter; the ternary documents "only facing overrides pending". `= false` default keeps domain tests compiling. `isFacingScreen || !wasEngaged ? .arm : .refresh` (:975) replaces the old second `route()` call — net simplification; moving into `AddresseeRoute` would still leave the classify-then-addressed `.arm` (:1000) in the VM.
N5 yaw correction source: `ConversationCamera` deliberately has no `RobotPreferences` dependency (init `(source:clock:)`; doc :55 independent of tracking preference). Composition closure reads `preferences.trackingYawCorrection` at call time (stepper changes immediate), matching `FaceTrackingCoordinator` per-observation read :193. `faces.count == 1` is attention-specific; tracking deliberately ranks among many faces, so moving it into `FaceTrackingGeometry` would be wrong. Reusing `selectFace` is the recorded decision and brings the range check on the correction (`FaceTrackingGeometry.swift:8`). Exposing a face list and deciding in the composition closure moves logic out of unit-testable code with no second consumer.
N6 two permission paths vs one owner: already one owner — live `FaceTrackingCoordinator(source: camera, …)` (`ConversationComposition.swift:36`) routes into `ConversationCamera.requestAuthorization()` deduped via `permissionTask` :64-79; settings pane calls camera directly (`CameraTrackingSettingsPane.swift:18`). Coordinator's second call runs only when the first did not (`.notDetermined` guard). Camera-first with denial via `FaceTrackingCoordinator.reconcile` :140 gives the same end state but conflicts with recorded ordering, same size, and still needs the tracking-path fallback for coordinators built without a camera (`FaceTrackingAppIntegrationTests.swift:22`, `RobotLifecycleIntegrationTests.swift:32`). The OR in `isAwaitingCameraPermission` :54-56 is still needed for those configurations and the gap before the camera's inner request starts in the `Task` wrapper :90. Cancellation guards not asymmetric: top guard :155 covers the tracking request (nothing suspends before it); re-check :162 covers the camera request after the await.
N7 overlap with reuse/simplification: `recordAttention` admission checks :199-211 mirror `FaceTrackingCoordinator.receive` :185-190; validating at each consumer is the right depth (tracking coordinator typed against `any FaceCaptureSource`, wired directly to fakes `FaceTrackingTestDoubles.swift:72`, cannot rely on camera validation); differences are recorded decisions (strict `completedAt <= clock.now`, `attentionStartedAt` floor). In `hasFreshFacingFace` :57, `eligible`/`attentionRequested`/`physicalGeneration != nil` are implied by `clearAttention()` on every transition; they copy the defensive lease check in `isSnapshotValid` :157-160; only live `source.authorization` adds coverage (`FacingAddressingTests.swift:181`). Neither is an altitude problem.
