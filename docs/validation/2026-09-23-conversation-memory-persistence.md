# 会話の記憶の保存・復元の検証

2026-09-23。`feature/conversation-memory-persistence`、main `392e763` から作成。
承認済みspecと実装計画は `docs/superpowers/` 配下。

## 実装した動作

- 正常に生成が完了した要約と確定往復を、端末内の単一スナップショットへ保存する。
- 次のプロセス/サービスで復元し、現在のtokenizerで再計数する。12K上限、8K付近の要約、直近2K保持は維持。
- 保存失敗は会話を継続できる警告。復元失敗は元ファイルを残し、新しい会話による上書きを止める。
- 忘却は生成・復元・保存再試行の終了を待ち、ファイルとRAMを消す。失敗時は再試行が成功するまで開始を止める。
- 同一ディレクトリに保護済み一時ファイルを作り、renameの成功を確定点とする。会話記憶は端末バックアップへ含めない。
- 通常アプリだけがファイル保存を既定にする。直接Gemmaサービスを作るテスト等は明示しない限りインメモリ保存。

2. 削除中の新規要求がネイティブ処理の終了待ちに入ってしまう。推論入口で削除中を先に確認し、即時拒否する修正で解消。

## 長い会話と要約済み記憶

実機で2回の自動要約と、その後のファイル保存・別サービスでの復元を検証。1件成功、失敗0、185.27秒。

- 保存世代はrevision=24。復元時の要約が保存スナップショットと完全一致し、保持した往復の順序も一致した。
- 要約後の生会話は2,331 / 2,332 tokens、要約は各512 tokens。往復単位で保持するため直近2Kは厳密な上限ではない。
- 復元後の回答: 「旅行先は金沢、好きな飲み物はほうじ茶です。」
- 要約が発生した返答の完了時間は27.91秒 / 50.83秒。保存追加後も要約待ち時間の問題は残る。この値は要約だけの計測ではない。
- 1回目の要約後は「おかえり」の指示に従ったが、2回目は「了解」と答えた。要約内にも反復・日付等の崩れがある。意味品質の改善をこの永続化機能の成功条件と混同しない。

この検証は同一プロセス内でサービスを作り直す要約復元確認。別プロセスでの永続化は前節の4フェーズで別途検証した。

## レビューと実装上の判断

独立レビューで指摘されたImportantは対応済み。保存中の消費側キャンセル、保存再試行中/ネイティブ終了待ち中の忘却、実際のファイル書き込み失敗、通常エラーをまたぐ保存警告のテストを追加した。Releaseの実機probeが本番記憶を消し得る経路も閉じた。

- 本番用の「コミット直前に失敗させる」テスト専用フックは追加せず、実際のファイル権限制限と注入ストアで失敗を再現した。任意のI/O命令単位の障害注入までは検証しない。
- Gemma直接生成時は既存テストとの互換性のためインメモリストアを既定とした。通常アプリのlive構成では必ずファイルストアを注入する。将来別の呼び出し元を追加する場合は永続化の選択を明示する必要がある。
- 準備/保存/忘却が同じ操作境界を共有するため、段階ごとの不完全な公開APIを残さずまとめて検証した。コミットの変更範囲は計画の細分化より大きい。
- 同一Simulatorに複数テストランナーを重ねた初期実行で一度bootstrap失敗があった。以後テストランナーを直列化し、全通常テストを再実行した。
- 保存データの一致とモデルの想起の正しさは別に判定する。全テスト成功が要約の意味内容の完全性を保証するものではない。

## 制約・未検証

- 保存I/O単体・cold-load単体の時間は未計測。上記9.12秒は推論と読み上げを含むため、保存・復元の性能値として使わない。
- 画面上の実タップによる削除ダイアログ操作は未実施。Coordinatorのダイアログ閉鎖競合は自動テスト、実機削除は通常ViewModel経由で確認した。
- ロック中の読み書き失敗からの復帰を手動で再現する確認は未実施。ファイル保護属性は実機で確認済み。
- 新しい会話を始めても直前の「会話の記憶を削除しました」という表示が残る軽微な表示上の問題は、レビューのMinorとして保留。保存・復元・削除の成否には影響しない。
- 同じディレクトリを複数の独立サービスが並行使用する構成は対象外。liveは単一の共有Gemmaサービスを使う。
- 生成中/保存未完でのプロセス終了は、最後に保存できた世代へ戻る。
