# Gemmaの自動要約を通常アプリへ反映

2026-09-21。main `4030e2b` から作成した `feature/gemma-auto-compaction`。

## 動作

- Gemma 4 E2B / GPU、コンテキスト上限12,288トークン。
- 確定した会話本文（利用者とAIのテキスト）の合計が8,192トークンに達したら、次の返答前に要約する。
- 直近2,048トークン以上を、利用者・AIの一往復単位で残す。古い会話と前回の要約から、最大512出力トークンの記憶を生成する。
- システム指示・要約・保持した会話から返答用セッションを再構築する。要約後は再び8K付近まで本文を蓄積する。
- 本文はモデルのtokenizerで計数する。推論の予算は、使用済みKV＋テンプレート適用後の入力＋出力上限＋32トークンの余裕で確認する。初回入力には遅延読み込みされる保持履歴も含む。区切りが多い場合は8K未満でも先に要約する。
- 要約・新しい往復の記憶は、返答が成功してキャンセルとの競合が解決した後に一緒に確定する。失敗時には元の記憶から再開できる。要約文は字幕・読み上げに流さない。
- 大きすぎる入力は `inputTooLong` として再入力を案内し、画面側も記憶を消さない。AFMの `contextExceeded` に対する既存処理は維持する。
- 本文が空の返答（空白のみを含む）では、一度だけ保存済みの記憶から再構築して再試行する。途中まで有効な返答が出た場合・通常の推論エラー・キャンセルは再試行しない。

`reset()` は要約と本文を両方消去する。既存UIの一時停止・バックグラウンド移行など、セッションをリセットする操作にも適用される。記憶はプロセス内のみで保持する。

## ランタイムの変更

Swiftパッケージ0.17.1が同梱するC APIをGemmaアダプター内で使う。実際のtokenizerと、会話を明示的に解放する機能が必要なため。アプリ側のReplyGenerating / AddressClassifying境界は維持する。

実機比較で複数のネイティブ会話を保持した際のKV復元に問題があったため、返答・要約・宛先判定は一つずつ作成・解放する。宛先判定の後は保存した記憶で返答を再構築する。キャンセル後も終端コールバックまで読み切り、古い会話の解放を終えてから次を開始する。

## 実機で見つかった挙動

長い会話の途中でネイティブ推論が本文を返さず終了するケースを2回再現した。元の記憶から会話を作り直し、同じ入力を送ると返答できたため、空返答のみ一度の再試行を追加した。ネイティブ内部で本文が出なくなる原因までは特定していない。

2回目の要約後、「おかえり」と指定しても「了解」と答えるケースがある。実機テストは会話の継続・予算・宛先判定との分離を検証し、この意味内容の評価は `greetingInstructionFollowed` と最終の想起回答として別に記録する。テスト成功は、要約による記憶保持や指示追従の完全性を保証しない。

## 最終実機測定

通常アプリのサービスを使った合成会話を連続実行。長会話テスト168.678秒、読み上げ等を含む短会話テスト31.797秒。

| 項目 | 1回目 | 2回目 |
| --- | --- | --- |
| 要約後に保持した本文 | 2,331トークン | 2,332トークン |
| 要約の実トークン数 | 512 | 512 |
| 要約開始を含む返答完了まで | 33.66秒 | 47.63秒 |
| 宛先判定後の「おかえり」指定 | おかえり | 了解 |

すべての送信で入力・出力余裕を含む予算が12,288未満。最大9,497トークン。途中の空返答1回は本番サービスの再試行で回復した。最終の想起回答は「旅行先は金沢で、好きな飲み物はほうじ茶です。」で、この2項目は正しく保持された。合言葉など、すべての記憶の保持を検証したものではない。
