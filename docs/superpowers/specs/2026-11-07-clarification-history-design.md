# 聞き返し前後の実際の発言を残し、文意で扱う（issue #29）

対象: [issue #29](https://github.com/kam6y/Cat-robot/issues/29)。main `1265a1070d8ad9691a8f7123fa18762a759b2e56`（#28 の squash 後）から `codex/issue-29-clarification-history` を作成。

「今日の天気はどう？」→「今の、ぼくに言った？」→ 返事、の流れを、実際に言われた言葉どおりに1回ずつ履歴へ残す。返事が肯定か否定かは決まった語の一覧ではなく文意で判断し、返答と要約のLLMがその流れを読めるようにする。

## 利用者と決めたこと（2026-11-07）

- シンプルに作る。宛先の確認結果（確認済み・否定・未確認など）を状態として保存・更新して渡すのではなく、猫とのやり取りを全部そのまま渡す。
- パターンマッチ（肯定語・否定語の一覧）では判定しない。言い方が少しずつ違うので、文意で判定する。
- 文意が否定のときも、猫が短く返答する。
- 確認待ちの間に、こちらを向いていない状態で返事が来たときは、宛先判定に元の発言と聞き返しを見せて判定する。この判定は最初からClaude Haikuで行う。
- 確認待ちの間に、こちらを向いていない状態で、宛先の手がかりがない別の話（「明日の予定は？」）が来たら、捨てて確認待ちだけ残す。

### issue本文から変わる点

issue本文は「アプリが確認状態を管理し、その結果を返答・要約LLMへ渡す」方針で登録されていたが、上の決定で次のように変える。

| issue本文                                                                | この設計                                                                                       |
| ------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------- |
| 確認待ち・確認済み・否定・未確認で終了の状態を元の発言に紐付けて保存する | 状態は保存しない。実際の発言の流れだけを残す                                                   |
| 猫が返事をしない否定の発言を、ユーザーだけの発言として保存する           | 否定でも猫が短く返すので、常に「発言と猫の返答」の往復になる。ユーザーだけの記録は作らない     |
| 否定や期限切れでは返答生成も会話回数の加算もしない                       | 否定の文意には短い返答を生成し、通常の返答と同じく回数に数える。期限切れは従来どおり何もしない |
| 長期メモ・要約の対象をアプリ側でも選ぶ                                   | アプリ側では選ばない。返答・要約の指示文で扱いを伝え、実モデルで確かめる                       |

「状態を持たない」は、肯定・否定の意味や応答済みの印を新たに保存しないという意味に限る。既存の15秒の確認待ち（`PendingClarification`）とその期限・振り分けは残す。

## 変える振る舞い

### 1. 確認待ちの間の振り分け（`AddresseePolicy`）

- 肯定語・否定語の一覧、元の発言への置き換え（肯定で元の発言を返答生成へ再送する経路）、否定語による確認待ちの取消（`.dismissPending`）をやめる。
- フィラーは従来どおり無視し、確認待ちを維持する。フィラーの一覧は今回変えない。
- こちら向きなら、実際の発言をそのまま返答生成へ渡す（従来どおり）。
- こちら向きでなければ、文脈つきの宛先判定へ渡す（次項）。
- 確認待ちかどうかと文脈をつけるかは、振り分けを始めた時点の期限の確認で決める。分類を待つ間に15秒を過ぎても、その判定は変えない。
- 確認待ちを解除するのは、返事を返答生成へ渡すとき（こちら向き、または文脈つき addressed）、文字入力、停止・新しい会話・全削除、既存の失敗終了（分類の失敗を含む）、期限切れのとき。
- 正常に分類できて notAddressed・ambiguous となった返事は捨て、確認待ちは期限まで残す。周りの人の発言で確認待ちが消え、その後の本人の返事に2回目の聞き返しをしないため。現行は分類に入る時点で解除しているので、これは振る舞いの変更である（実装判断）。
  - 残すのは同じ元の発言・同じ期限・同じ期限監視で、作り直したり15秒を延ばしたりしない。
  - 文脈と「確認待ちから始まった入力か」は分類を始める前に固定する。分類の後に確認待ちが残っているかで判断しない。
  - 分類中に期限が過ぎた場合、notAddressed・ambiguous ならその入力は0で、聞き返しもしない。期限切れの確認待ちを戻さず、次の入力に文脈をつけない。addressed なら、既存の所有世代・取消の確認を通ったときだけ今回の発言で返答を生成する。停止・文字入力・新しい会話・削除に負けた古い完了は何もしない。

15秒は、アプリが返事を待ち、文脈つきで判定する期限である。履歴には発言の時刻も期限切れも残さないので、返答のLLMは期限内の返事か期限後の返事かを区別できない。期限後でも、こちら向きで届いた「うん」などは、履歴に基づいて元の発言への返事として解釈されることがある。この設計での「返事がなかった発言」は、履歴上で猫宛てと認められていない発言の扱いを指し、期限切れの状態をLLMへ伝えるものではない。期限後に元の発言へ答えないことは要件にしない。

### 2. 文脈つきの宛先判定（Claude Haiku）

- 確認待ち中に限り、「猫が直前に聞き返した元の発言」と固定の聞き返し「今の、ぼくに言った？」を文脈として渡し、端末内モデルの有無にかかわらずClaude Haikuで判定する。確認待ちでないときの振り分け（端末内モデルが使えれば端末内、使えなければHaiku）と、端末内分類器の指示は変えない。
- 判定するのは「今回の返事が猫への答え、または猫に向けた発話か」。元の発言の宛先は判定しない。たとえば「いいえ、あなたには言ってない」は、元の発言は猫宛てではないが、今回の返事は猫への答えなので addressed とする。
- 聞き返しへの答えとも猫宛てとも読めない、宛先の手がかりがない別の話（「明日の予定は？」）は ambiguous とする。猫を呼ぶなど手がかりがあれば addressed。
- Haikuの判定が失敗したら、既存の分類失敗の経路に従う。端末内モデルへ切り替えて判定し直すことはしない（実装判断）。
- 確認待ち中にこちらを向いていないときは、端末内モデルが使える端末でもネットワーク呼び出しとHaikuの利用料が発生する（利用者が了承）。遅延・費用は未計測。
- 文脈は分類器への入力にだけ使う。返答生成のpromptや保存する履歴に連結しない。
- 現行は分類に入る時点で確認待ちを解除しているが、上のとおり分類の結果が出るまで解除しない。
- 確認待ち中の ambiguous は従来どおり捨て、聞き返しを重ねない。notAddressed も何も追加しない。

### 3. 返答生成へ渡す内容

- promptは常に今回の実際の発言。元の発言を再送しない。
- 元の発言と聞き返しは、既存どおり聞き返しの読み上げが正常に終わった時点で1往復として記録済み（#23）。この外部記録でセッションは作り直されるので、記録後の履歴を含むセッションに今回の発言を1回だけ渡す。復元した履歴と今回のpromptの両方に同じ発言を入れない。
- 返答用の固定指示（`ConversationInstructions`の前方）に次の扱いを1項目足す。
  - 猫が「今の、ぼくに言った？」と聞き返した後の利用者の返事は、意味で判断する。猫宛てだと認めたら元の発言に答える。否定されたら短く受け止め、元の発言には答えない。返答生成へ届いた別の話にはそれに答える。
  - 否定された発言や返事がなかった発言を、未解決の質問や利用者の事実として扱わず、rememberで保存しない。
- 固定指示の前方が変わる。実際のプロンプトキャッシュの再利用・費用・待ち時間への影響は未計測。

### 4. 要約（`ConversationSummaryRequest`）

指示に同じ扱いを1文足す。猫が聞き返した発言は、利用者が猫宛てだと認めた場合だけ、猫への質問や利用者の事実として扱う。否定された発言・返事がなかった発言は、未解決の質問として残さない。

圧縮は往復単位で古い側を要約へ回すため、「元の発言→聞き返し」が要約対象、「うん、私のこと→猫の返答」が残る側に分かれることがある。このとき要約のLLMが肯定を見られないまま元の発言を落とさないよう、圧縮後も残る直近の往復を「解釈のための参考。要約には含めない」として要約の入力に添える。要約する対象は従来どおり古い側の往復だけで、保存形式は変えない。

要約の入力は、参考として渡す残す側の実際の文字数だけ増える。残す側は往復単位で切り上げるので、最低限残す文字数（現行4,000文字）を超えることがある。参考を短く切ると必要な肯定・否定をまた落とすので、切り詰めない。費用・待ち時間への影響は未計測。

要約対象が否定された発言や肯定のない発言だけで、残すことが無い場合がある。現行は空の要約を生成の失敗として扱うので、「残すものが無い」という正常な結果を生成の失敗と区別できる形で受け取る。方式（構造化出力で0件を許す等）は実装計画で決める。単に空の検査を外すことはしない。この場合も次の返答が失敗や代替に落ちないこと。

## 変えないもの

- 保存形式（`ConversationMemoryTurn`の`prompt`と`response`、schema 1）。移行は不要。
- 15秒の確認待ちと期限、30秒・最大5分の会話継続窓、顔向きと人数の条件。会話継続窓は、否定への短い返答の後も現行どおり開始・更新される。
- 聞き返しを記録する時点（読み上げの正常完了後）。読み上げの途中・失敗・取消・未完了では記録しない。
- 履歴の渡し方（system指示文の中の「利用者:／猫:」の文字列）。役割付きのtranscriptで復元する変更はしない（#27の範囲）。
- 保存失敗時のメモリ内保持・未保存表示・再試行、所有世代と削除の防御、外部記録後にセッションを作り直す動作。
- 端末内の代替モデル（Claudeが使えないとき）は、Claude側の履歴と聞き返しを引き継がない。代替時は「はい」等だけでは話題を失いうる。既存の、どの続きの発言にも共通する制約として今回は直さない。

## 分岐ごとに追加される往復

「追加」は、今回処理する入力から履歴へ加わる往復の数。既に記録した「元の発言→聞き返し」は、否定・期限切れ・後の除外で消さない。圧縮・新しい会話・全削除は別の処理。

| 場面                                                     | 振り分け                                                                                     | 追加                                        | 会話回数 |
| -------------------------------------------------------- | -------------------------------------------------------------------------------------------- | ------------------------------------------- | -------- |
| 音声の空・フィラー                                       | 無視（確認待ち中なら維持）                                                                   | 0                                           | 0        |
| 確認待ちでない・こちら向き／会話継続窓内／分類 addressed | 実際の発言で返答生成                                                                         | 生成の正常完了で1                           | 1        |
| 確認待ちでない・分類 notAddressed                        | 無視                                                                                         | 0                                           | 0        |
| 確認待ちでない・分類 ambiguous                           | 聞き返し                                                                                     | 読み上げの正常完了で1（元の発言・聞き返し） | 0        |
| 確認待ち中・こちら向き                                   | 実際の発言で返答生成                                                                         | 生成の正常完了で1                           | 1        |
| 確認待ち中・向いていない・文脈つき addressed             | 実際の発言で返答生成                                                                         | 生成の正常完了で1                           | 1        |
| 確認待ち中・文脈つき notAddressed／ambiguous             | 返事を捨て、確認待ちは期限まで残す                                                           | 0                                           | 0        |
| 確認待ちの期限切れ                                       | 何もしない                                                                                   | 0                                           | 0        |
| 文字入力（確認待ちの有無によらない）                     | 確認待ちがあれば解除し、入力した文のまま返答生成。空の入力は送らない。フィラーの選別はしない | 生成の正常完了で1                           | 1        |
| 分類の失敗、聞き返しの未完了・失敗・取消                 | 既存の経路                                                                                   | 0                                           | 0        |

- 表の会話回数1は、Claudeの空でない生成が正常に終わったときに限る。代替モデルの場合は下記のとおり。
- 返答は生成が正常に終わった時点で履歴と会話回数に確定し、読み上げの完了を待たない。確定後の読み上げ失敗・停止・取消で1を戻さない。確定前の失敗・取消は0。
- Claudeが表示前に失敗して端末内の代替が成功した場合と、日次上限で代替した場合は、通知文と本文を外部往復として1追加し、Claudeの会話回数は0。代替も失敗・空なら0。本文が一部出た後のClaudeの失敗は代替しない。
- 保存に失敗しても、メモリ内には追加し、未保存表示と再試行を維持する。

## 確認すること

### 自動テスト

- `AddresseePolicy`: 肯定語・否定語の一覧を外した後の、確認待ち中の振り分け（こちら向き／向いていない）、フィラーで確認待ちを維持、期限の境界。
- 分類器の振り分け（実際の組み立てで確認）: 確認待ち中・向いていないときは、端末内モデルが使えても文脈つきのHaikuだけを呼ぶ。確認待ち中・こちら向きは分類器を呼ばない。確認待ちでない・期限切れのときは従来どおり（端末内が使えれば端末内、使えなければHaiku、文脈なし）。確認待ち中のHaikuの失敗では端末内で判定し直さず、既存の失敗終了で確認待ちを解除する。通常の入力のHaiku判定に、聞き返しへの答え用の規則を持ち込まない。
- 会話VMと記憶サービスの統合:
  - 文意の肯定・否定・別の話で、返答生成へのpromptが実際の発言であること。元の発言が再送されず、履歴に重複しないこと。
  - 否定の返事にも返答が生成され、その往復が保存されること。ユーザーだけの記録を作らないこと。
  - 文脈が分類器にだけ渡り、promptと履歴に入らないこと。確認待ち中の ambiguous・notAddressed で何も追加せず、確認待ちが残り、続く本人の返事が文脈つきで判定されること。期限内に周りの発言を何回はさんでも、期限が延びず、聞き返しを重ねず、本人の返事が同じ元の発言の文脈で処理されること。分類中に期限が過ぎる場合（上記）。
  - 期限の境界（振り分け開始時点で判定）、文字入力、代替モデル、生成確定の前後の取消、保存失敗・再起動・復元、停止・新しい会話・全削除との競合。
- 圧縮: 「元の発言→聞き返し」が要約対象、肯定・否定の往復が残る側に分かれる区切りで、残る側が参考として要約の入力に入り、要約対象には入らないこと。残すものが無い要約が正常に扱われ、生成の失敗とは区別されること（既存の「要約が失敗したら記憶を確定しない」回帰とあわせて）。
- 既存の回帰対象を維持する: 自然な肯定「言ったよ」の続き、聞き返しの復元、聞き返しの未完了で記録しないこと、保存失敗と再試行、停止・削除の競合。従来の「否定では記録しない」テストは新しい要件に合わせて更新する。

### 実モデル

- [ ] 文脈つきのClaude Haikuの判定で、短い返事（「はい」「うん」「いいえ」「ううん」）、言い方の違う肯定（「言ったよ」「そうそう、天気の」）・否定（「いいえ、あなたには言ってない」「違うよ、ママに言ったの」）・猫を呼ぶ別の話は addressed、手がかりのない別の話（「明日の予定は？」）は ambiguous、他の人宛て・周りの会話は notAddressed か ambiguous が期待値。短い返事と言い方の違う肯定・否定は addressed が必須。元の発言が猫宛てでないことと、今の返事の宛先を取り違えないことが要点。実行回数と合否の基準（必須の例が何回中何回 addressed になればよいか）は実装計画で実行前に決め、不合格なら指示文を直して測り直す。
- [ ] 返答のLLMで、肯定のとき元の話題に答え、否定のとき短く受け止めて元の質問に答えないこと。
- [ ] 要約のLLMで、否定された発言や返事がなかった発言が、未解決の質問や利用者の事実として残らないこと。肯定が残る側にある区切りでも、認められた元の発言を落とさないこと。返答時にrememberが否定された発言を保存しないこと。

### 実機・文書

- 通常版を実機に入れ、利用者が肯定・否定・別の話の流れを確認する。
- 文書の索引（`docs/README.md`）にこのspecを加え、`docs/superpowers/specs/2026-11-06-neutral-history-design.md`の「肯定で2往復になる」記述が古くなる旨を示す。分岐図（`docs/application-flow.html`）の確認待ちの行も更新する。

## 進め方

Codex・Claudeのペアで進める。spec（この文書）はClaudeがDriver、CodexがNavigator。spec承認後に実装計画を作り、テストの区切りまたは15〜30分ごとにDriver／Navigatorを交代する。ソースを編集するのはその時のDriverだけで、ビルド・試験中は双方が入力を固定する。xcodebuildと実機はCodexが担当する。

最後にClaudeの実際の`/simplify`（修正を適用しない4観点）とCodex側の独立レビュー1名、相互のreceivingを行う。mainへのsquashまで進め、pushは利用者の承認を得てから行う。
