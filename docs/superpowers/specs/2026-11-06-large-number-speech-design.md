# 大きな数字と数値表記の読み上げ（issue #24）

## 採用方針

main `b050575f88b6f14f520f3ee968c42c0ad6021e3c` から `codex/issue-24-japanese-number-speech` を作成した。大きな数量と数値表記を自然に読み、表示・記憶の原文、声、モデル、8steps、速度、CPU並列数は変えない。2026-10-29に採用した「日本語の全文カナ化を避ける」方針を守る。

実機で原文・数字部分のカナ・数字部分の漢数字を同じ声で合成し、利用者は **C＝漢数字** を選択した。`1500000円`→`百五十万円`、`３億５０００万`→`三億五千万` とする。また、利用者は従来の小数・%・時刻・電話番号・IDにも読みの問題を確認したため、これらも修正対象に含める。

利用者の「ライブラリを使い、独自実装をできる限り避け、Claudeと方針をすり合わせる」という指示に従い、既存jpreprocess、Foundation/ICU、NeMo Rustなどを比較した。NeMo Rustの固定タグv0.3.1では通常APIと日本語FSTを実行した。iPhone対応は可能だが、FSTは今回の `1,500,000` を `一,五百,零零零`、電話を数量読み、IDを基数読みとし、必要な境界処理を減らせなかった。Foundationも整数以外の用途判別は担わない。

Claudeとの合意は **固定jpreprocess0.15の標準NJDを使い、読み表・数詞分解を自前で持たない** こと。整数は前処理後の表層、その他は標準の発音を選ぶ。実際の公開API・実辞書の出力を根拠にし、未提示の設計への利用者承認は主張しない。

## 契約

- 既存 `protected_ranges` を維持し、URL・メール・バッククォートを保持する。`IDENTIFIERS` の最大語を再利用し、Latin語・未知識別子・他script・結合文字から数字だけを奪わない。カンマを最大語のregexに加えない。
- 5桁以上の独立した整数、厳密な3桁区切り（半角・全角カンマ）、万・億・兆・京を含む数量をNJDへ渡し、漢数字の表層を使う。前処理前の未確定発音を理由に数を拒否しない。
- 小数点が1つの数字語と%は、区間全体を標準NJDで読む。`3.14`→`サンテンイチヨン`、`25%`→`ニジューゴパーセント`。独自の小数読みや単位の読み表は作らない。
- 日本の10/11桁の0始まりの電話形式は区間全体を標準NJDへ渡し、その桁読みと区切りを使う。明示的IDは一箇所のラベル規則（ID/No./番号/コード/電話/郵便と空白・コロン・助詞）で受理し、実際の1文字入力を辞書APIへ渡し、前後と各桁の間を段落で区切り、既存Supertonicが各桁を別区間で合成する。区切りも展開後2000文字に含める。偽の番号文脈・読み表は使わない。ラベルごとに挙動を検証する。
- 有効なH:MM（0〜23時・2桁の0〜59分）は時・分の表記へ整える。両フィールドの漢字化はNJDを使い、先頭0を除き、0分を省略する。助数詞の発音規則は自前で実装しない。
- 不正な桁区切りや数字を挟む単位順、先頭0を持つ曖昧な整数、バージョン、日付、数値間スラッシュ、無効な時刻、負符号・範囲は保守的に保持する。桁区切りに続く小数・Latin末尾や単位に続く非純数字を、途中まで変換しない。`+`の既存言語化は維持する。
- 小さい助数詞 `3人で25個`、年 `2026年`、整数の温度例は従来入力を保つ。大きな数の外側の日本語・助数詞も原表記を保つ。裸の大きい整数を任意のIDとして意味理解できるとは主張しない。
- NJDの次の単位 `𥝱` はSupertonicの文字表に無いため、数量の数字部分は文字として24桁までとし（単位を掛けた数学的値の上限ではない）、それ以上は全体を保持する。辞書・モデルに未対応の文字を新たに送り込まない。
- 入力32768bytes、Swiftの入力・展開後2000文字、NUL・UTF-8・辞書失敗・取消・所有権の契約を維持する。数字の欠落・切り詰め・操作失敗後の黙った原文フォールバックはしない。
- C ABI、モデル、辞書、依存バージョンは変えない。Rust変更後はiPhone arm64、Simulator arm64/x86_64を再構築し、ソースと生成物のreceiptを検証する。新しいSwiftファイルや不要なproject再生成は加えない。

## 検証と完了

実辞書でRED→GREENを確認し、Swift→C ABI→辞書の変換結果、展開制限、長文の桁区切り分割防止、文再生へ渡る原文と音声入力を検証する。同じSupertonic/F1/8steps/CPU2で実機合成し、大きな数量のC選択と、小数・%・時刻・電話・IDの修正後の聴取を分けて記録する。音声生成だけで自然さの合格とはしない。私的な会話履歴は使わない。

agmsgでClaudeとpairを行い、最後に実際の `/simplify` 4観点と1名の独立subagent reviewを実行する。双方の初回報告を保持して相互に `receiving-code-review` を行い、根拠のある指摘を修正する。全件試験、通常署名版の実機更新、mainへの1コミットsquash・non-force push・issue完了確認まで進める。

IDの音声は漢数字・ひらがな・段落区切りを各3回比較し、利用者が段落区切りを選択した。9桁の例の合成約5.4秒・再生約17.4秒を選択前に明示した。IDのこのケースはS1の2.5秒目標を満たさないが、利用者の明示的な聞き取り優先の選択として採用し、S1自体の定義は変えない。段落のない数量・小数・電話の経路は維持する。
