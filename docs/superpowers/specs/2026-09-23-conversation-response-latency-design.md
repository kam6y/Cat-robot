# 返答が聞こえるまでの待ち時間を短くする設計

2026-09-23 / written spec review待ち。
ブランチ: `feature/conversation-response-latency`。
起点: main `066e3a6d75b9a75e1819124d056d59b406807d2b`。

## 1. 目的と合意の範囲

利用者は、合成音声モデルの選定より先に、会話の返答までの待ち時間を改善することを選んだ。今回の依頼はfeatureブランチ作成とspec作成まで。実装とmainへの統合は、この文書を作ったことだけでは開始しない。

主な成功指標は「利用者が話し終わってから、実際の返答音声が始まるまで」。全文の読み上げ終了時間、最初の字幕、生成開始、生成終了を混同しない。単なる相づちや効果音で速く見せるのではなく、生成した回答を早く届ける。

設計上の前提は、Gemma 4 E2B、現在のApple合成音声、12K上限／8K付近で要約／直近2K以上の往復保持を維持すること。通常の会話を優先し、要約が発生する長い会話は別集計する。

## 2. 現状と根拠

- `ConversationViewModel.generateReply` / `generateTypedReply` は累積スナップショットを字幕へ反映し、ストリームが正常終了してから最終全文を読み上げる。
- Gemmaはネイティブの差分を連結して累積スナップショットを発行する。正常生成後の記憶確定とファイル保存が終わるまで、ストリームを終了しない。したがって現在の音声開始は、全文生成と保存の両方を待つ。
- `AppleSpeechSynthesizer` は同時に一つの読み上げを管理する。開始・単語範囲・終了・キャンセルを通知し、古いrunの終了が新しいrunを止めない保護がある。
- 既存の`ConversationLatency`は、高速経路／宛先分類経路の最初の字幕と音声開始を別々に計測する。ただし起点は`beginClosingCapture`。認識更新時刻は実際の音声終端ではなく、認識遅延を含んだ時刻である。
- 無音待ちの設定は1.2秒、最大発話時間は20秒。宛先分類の後は返答用のネイティブ会話を再構築する。分類・要約・返答を同じGemmaで並列実行しない。
- 前回の約9.12秒は、復元を伴う文字入力から読み上げ完了までの値。返答開始時間や復元単体の値には転用しない。
- 要約を含む返答では27.91秒／50.83秒を観測した。これも要約単体の値ではない。文単位の先行読み上げで、生成前の要約待ちが消えるとは主張しない。
- USB接続時に端末マイクの入力が全てゼロになり、ボイスメモも無音となる現象を観測。USBを外すとボイスメモとCatRobotの音声応答が復旧した。Mac/iOSの具体的な原因は未特定。性能評価の前に入力が正常か確認する。

基準コードの直近main統合テストは296件中292成功・実機専用4スキップ・失敗0。今回のspec作成では製品コードを変更せず、この基準結果を参照する。実装開始時には必要な基準計測を新たに取得する。

## 3. 比較した方針

| 方針 | 利点 | 制約 | 判断 |
| --- | --- | --- | --- |
| A. 計測追加と逐次処理の小さな短縮のみ | 既存の成功・停止境界を維持しやすい | 全文待ちの構造は残る。効果は計測次第 | 全方針の土台として採用 |
| B. 最初の一文を先行して読み上げる | 通常の一〜二文の返答に適合。生成と音声を重ねられる | 途中で失敗すると、未完の返答を一部聞く場合がある | 今回の推奨方式 |
| C. 任意長の断片を連続投入／別TTSへ移行 | 長文や音声生成自体の最適化余地 | 文の途切れ、抑揚、キュー、モデル共存の検証範囲が広い | 今回は対象外 |

まず現行版を計測し、Bを同一条件で比較する。指標を満たさなければ既定動作を切り替えず、改善しなかった要因を報告する。無音待ちの短縮やモデル変更を、結果が悪かったときに黙って追加しない。

## 4. 利用者から見える動作

1. 音声入力の確定・宛先判定は現在の方針を維持する。文字入力も同じ生成・読み上げ方式を使う。
2. 字幕はこれまでどおり全文の累積表示を更新する。
3. 生成途中で最初の読み上げ可能な一文が確定したら、全文を待たず読み上げる。先行再生は一回だけ。
4. 残りの文字列は生成が正常終了した後、先行再生の終了を待って続けて読み上げる。先行再生が終わっても生成中ならマイクを再開しない。
5. 一文しかない、適切な区切りがない、または先行読み上げ非対応の生成サービスでは、従来どおり最終全文を読み上げる。文字数や時間だけで単語を切らない。
6. 実際の音声開始イベントで「話している」表示と口の動きを開始する。文間で音声が途切れたら口を閉じ、残りを待つ間は生成中の状態を示す。音声をキューへ渡しただけで発話開始とみなさない。
7. 返答生成と必要な読み上げが全て終わってから、会話継続状態を更新し、元の経路に従って聞き取り再開または一時停止へ進む。

先行読み上げのために、相づちを追加したり、回答の内容・長さ・プロンプトを変更したりしない。

## 5. 生成文の分割と対応サービス

`ReplyGenerating`の累積スナップショット契約は維持する。生成済みの接頭部分が変わらないことを保証する能力を明示し、既定値は非対応、Gemmaのみ対応とする。AFMと既存の置換型fakeは全文完成後に読む。UI上にモデル切り替えは追加しない。

最初の一文の抽出は純粋な処理として独立させる。

- 元の累積文字列と、読み上げに渡した接頭部分を保持する。差分ではなく接頭部分の範囲で重複を防ぐ。
- 日本語の`。`、`！`、`？`とASCIIの`!`、`?`を文末候補とする。ASCIIの`.`、読点、改行だけでは切らない。小数・URL・略語を途中で読まないため、英語のピリオドによる先行分割は対象外。
- 対応する括弧・引用符（`「」`、`『』`、`（）`、`()`、`“”`、`""`）の内側だけで終わる候補は、閉じ記号が揃うまで保留する。閉じ記号や連続する終止記号は先行文へ含める。
- スナップショットの末尾にある文末候補は、後続の内容文字が届いて境界が確定するまで保留する。生成がそのまま終わった場合は最終全文として読む。括弧が閉じない場合も強制分割せず、正常終了時の全文へフォールバックする。
- 空白だけ、記号だけの接頭部分は読まない。原文から取り出した部分を読み、残りと結合した文字列が最終スナップショットと一致することを保証する。
- 同じスナップショットの再通知は何もしない。先行読み上げ後にその接頭部分が書き換わったら契約違反とし、残りを読まずエラーにする。既に聞こえた音声は撤回できないため、読み直しによる帳尻合わせをしない。

今回は「先行一文＋正常終了後の残り」の最大二つだけを扱う。全文への文字変換・Markdown整形・文章の再生成は追加しない。

## 6. 非同期処理と責務

生成ストリームの消費と先行音声の消費を、一つの返答ターンが所有する。ViewModelの音声経路と文字経路で分割・重複防止・キャンセルの中核を共有する小さなコーディネータを設ける。ViewModel全体の再設計は行わない。

- 字幕更新と先行文確定を扱う生成側は、音声終了をawaitして生成の消費を止めない。
- 音声側は`SpeechSpeaking.speak`の既存契約を使う。一度に一つだけ読み、先行文と残りを重ねて発声しない。新しいTTSモデルやネイティブキューAPIは不要。
- 生成完了・音声完了の両方を合流条件とする。fire-and-forgetで後続の発話を残さない。各イベントに既存のgeneration／turnIDの所有権を適用する。
- 一時停止、バックグラウンド、音声経路変更、文字入力への切り替え、忘却は、生成の消費と音声の両方を止め、待機中の残りを破棄する。
- 生成の消費が中断されたら既存のGemmaキャンセル経路へ伝える。ネイティブ処理の終了待ちとセッション寿命の規則は維持する。`reset()`で止める実装は禁止する。現在のresetは保存済み記憶を消すためである。
- 後から届く旧ターンのイベントが新しい字幕・口・マイク状態を更新しない。停止と新規入力が重なっても、新しい音声を旧ターンの終了処理で止めない。
- 宛先分類・要約・返答を並行実行しない。並行化するのは返答生成とApple合成音声だけ。
- 定型の呼びかけ返答・聞き返しは既存の単発読み上げを維持し、生成回答の性能集計と分ける。

## 7. 途中失敗と保存済み記憶

先行読み上げは、返答生成の成功確定より先に一部の内容を利用者へ届ける。この振る舞いの変更を明示的に受け入れる必要がある。

- 生成失敗時は、進行中の先行音声を停止し、未再生部分を破棄して既存のエラー回復画面へ進む。先に出た字幕は失敗状態として扱い、返答全体が成功したように見せない。
- 一部を読んだ後に全文を再試行・再読み上げしない。既存の「可視出力がゼロの空返答だけ一度再試行」は維持する。
- TTS失敗時は生成側も中断し、両方の処理を回収して既存の音声エラーを示す。音声エラーを認識エラーや保存エラーに置き換えない。
- 記憶の確定点はGemmaの正常生成成功のまま。先行文だけを保存しない。生成確定前の失敗・停止では新規往復と候補要約を確定しない。
- Gemmaが既に生成を確定していた場合、その後のTTS失敗・一時停止で記憶を巻き戻さない。保存処理も最後まで行う。利用者が一部しか聞いていなくても、確定済みの全文が記憶に残る場合がある。
- 保存失敗は既存どおり非致命の警告。読み上げ済み部分を再実行せず、保存再試行・忘却の競合保証を維持する。
- 忘却は両方のUI処理を停止したうえで既存のサービス所有タスクに委ねる。削除後に古い字幕・音声・ファイルを復活させない。

## 8. 計測の定義

既存signpostを再利用・拡張し、単調増加時計、相関ID、段階、結果コード、文字数／token数などの量だけを記録する。利用者の音声・認識文・返答文は通常ログへ出さない。テスト用合成文の回答はテストartifactだけに保存する。

| 区間・時点 | 測るもの |
| --- | --- |
| 実音声の終端→最初に聞こえる返答 | 利用者が体感する待ち時間。既知の合成音声と外部録音の波形で評価 |
| 最後の認識更新→終了判定 | アプリ内の終了判定待ち。実音声の終端の代用とは表記しない |
| 終了判定→認識停止完了 | 音声入力の終了処理 |
| 宛先判定開始→終了 | 必要な経路だけ。非応答・曖昧も別結果として残す |
| 生成要求→最初の字幕／先行文確定／生成終了 | 生成と分割の待ち。要約・セッション再構築の有無を区別 |
| 要約／セッション再構築／保存の各開始→終了 | 非公開の内部待ちの内訳。生成終了とストリーム終了は分ける |
| TTS投入→開始イベント | 合成音声の起動待ち。先行文と残りを区別 |
| 返答全体の音声終了、文間の無音 | 先行再生による副作用を評価 |

`SpeechEvent.started`を自動計測の音声開始代理値とする。欠落時に`willSpeak`を使った測定は代用フラグを付けて別集計する。キュー投入、字幕表示、読み上げ完了を音声開始に代用しない。実音声終端を測れなかった実行では、アプリ内の区間だけを報告し「発話終了から」とは称さない。

コールド起動・通常の高速経路・宛先分類経路・履歴再構築・要約発生を分類する。キャンセル／エラー／非応答を黙って除外せず件数を併記し、成功時の遅延統計と分ける。

## 9. 実機比較と採用条件

iPhone 16 Proでmain基準版と候補版を比較する。固定モデル・同じ声・音量・合成会話・保存スナップショットを使い、初期履歴を各条件で揃える。端末温度、OS、電源状態を記録し、基準→候補だけでなく候補→基準も交互に実施する。

### 評価セット

- 二文以上の返答が得られる固定質問10種類を各版3回以上。先行文が生成終了前に確定した割合も報告し、都合のよい回答だけを選ばない。
- 一文返答・区切りなし・数字・URL・引用を含む回答の短い対照セット。
- 高速経路と宛先分類経路を分けて実行。文字入力は音声認識を除いた処理の比較用とする。
- コールド起動は各版3回以上の参考値。通常セットに混ぜない。
- 要約を最低2回発生させる長会話を別枠で確認し、要約後の保存・復元・想起を回帰確認する。今回の速度改善の達成値へ混ぜない。
- 保存先はテストUUIDで隔離する。本番の会話記憶を性能fixtureへ置き換えたり削除したりしない。
- 音声評価前にボイスメモとCatRobotで入力を確認する。USB接続で無音になる場合はUSBを外し、無線での開発接続または切断状態で計測する。無音の試行を性能結果に採用しない。

### 既定採用のゲート

以下は実測済みの性能ではなく、設計上の採用基準。

1. 通常の固定質問セットで、最初の音声開始の中央値を基準より20%以上かつ0.5秒以上短縮する。主比較の起点は生成要求とし、別途測った実発話終了からの結果も示す。経路別の結果を併記する。
2. 高速経路／分類経路の各通常セットで、p90が基準より0.5秒を超えて悪化しない。小標本のp90は参考分位と明記し、個別の測定値も残す。
3. 短い一文の対照セットでは、音声開始の中央値と全体読み上げ終了の中央値が基準より0.3秒を超えて悪化しない。
4. 二文の間の無音は、通常セットのp90で1秒以下を目標とする。超える場合は試聴結果も添え、開始だけ速くして会話全体を不自然にする方式を自動採用しない。
5. 重複・脱落・順序逆転・同時発声・早すぎるマイク再開・キャンセル後の音声継続がテストでゼロ。二文セットの全回答を試聴し、文境界による不自然な読みを記録する。
6. 全通常回帰テストが通り、保存・復元・忘却・音声割り込みの保証を維持する。

採用基準を満たさなければ計測と比較結果までを成果とし、通常アプリの動作を切り替えない。計画段階で値を変更する場合は、測定後に都合よく変更せず理由を明示する。比較専用の旧／新方式選択はテスト構成へ閉じ、利用者向け切り替えUIは設けない。

## 10. 必須の回帰テスト

- スナップショットが一文字ずつ届く、文末と閉じ括弧が別々に届く、同じ内容が再通知される、引用が閉じない、一文だけ、区切りなし、空出力。
- 一文目のTTS開始が生成の終端より前であることをgateで証明。先行再生中も生成を消費し、字幕が更新されること。
- 一文目が先に終わる場合と生成が先に終わる場合の両方で、残りが一度だけ順番に再生されること。
- AFMや接頭部分非保証のサービスは全文確定後にだけ読むこと。保証違反は誤った残りや重複を読まず停止すること。
- 先行再生前／中／後の生成失敗、TTS開始失敗・途中失敗、キャンセル、バックグラウンド、経路変更、即時の次ターン開始。
- 生成確定前の停止は未保存、確定後の停止は保存完了、保存失敗は警告、忘却後に旧処理が復活しないこと。
- 音声入力と文字入力の両方で、生成と全音声が完了するまで次のマイクが開始されず、旧イベントが新しいターンへ影響しないこと。
- 計測の開始・終了が各一回、非応答や途中失敗も終端を持つこと。認識文と回答文が計測イベントに含まれないこと。

## 11. 変更対象と範囲外

主な対象は`ConversationLatency`、`ConversationViewModel`、`ReplyGenerating`の能力宣言、Gemma内部の段階計測、新しい返答再生コーディネータと先行文の抽出処理、および対応する単体・統合・実機テスト。必要なら`ConversationViewState`の表示遷移を調整する。Xcodeプロジェクトは既存の生成スクリプトを使う。

対象外: TTSモデル／声の選定、Gemmaモデルやtoken上限の変更、要約の先回り・小分け・バックグラウンド実行、保存形式の変更、分類の省略、無音待ちの短縮、同時に聞きながら話す割り込み、音声認識エンジンの交換、ネットワーク推論、USB音声問題のOS側修正、ViewModel全体のリファクタリング。

## 12. セルフレビュー

目的は返答開始の短縮であり、全文終了や字幕開始を成功指標へすり替えていない。全文生成前に音声が届くという意味の変化と、生成成功を基準にした保存契約を明記した。要約待ちは今回の先行読み上げでは解決しないことを分離した。提案には新しい合成音声モデルも無制限の音声キューも不要であり、一つの実装計画に収まる範囲とした。
