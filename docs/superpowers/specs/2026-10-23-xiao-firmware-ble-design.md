## 1. 目的と背景

猫ロボットの首（ヨー・ピッチの 2 軸、DS3218 サーボ直結）を iPhone アプリから BLE で動かすための土台を作る。サブ計画 1 で Claude 会話エンジンは完成し、アプリは返答に合わせて首を動かす準備ができた。しかしロボット側には動作を受け付ける仕組みが無い。XIAO ESP32C3 に入っているのはハード製作時の試験プログラム（起動時に `BOOT AC5 OUTPUTS_OFF pins=3,5` と出す）だけで、利用者はこれを上書きしてよいと決めた。

本サブ計画の成果物は三つ。

1. XIAO ESP32C3 のファームウェア（BLE 受信、サーボ駆動、可動域・速度の強制、ウォッチドッグ、キャリブレーション保存、シリアル経路）
2. プロトコル版 1 のバイト列契約（サブ計画 3 がそのまま実装できる粒度）
3. iOS 側が無くてもロボットを動かして検証できる Mac 用の試験ツール（BLE クライアントとシリアル CLI）

利用者はファームウェア開発が初めてで、書き込み環境も Mac に無い。コマンドは claude が打ち、手順書は日本語で残す。

## 2. ゴール・非ゴール・アンチゴール

### ゴール

- 要件定義書 §7.3〜§7.6 の機能をすべて実装し、実機で受入基準（§5）を満たす
- 【利用者】「各種そぶり（頷き・横振り・かしげ・見上げ・うつむき・正面）が実機でできる」ことが「できた」の基準
- 【利用者】頷きは人の相づち程度の速さ（1 往復 1 秒前後）。要件定義書の速度上限は引き上げる
- 純粋ロジック（符号化・復号、制限、軌道、安全状態機械）は Mac 上の単体テストで実機なしに検証できる
- サブ計画 3 の実装者が本書だけで BLE クライアントを書ける

### 非ゴール

- iOS アプリ側の変更（サブ計画 3・4）
- 顔追尾・待機微動・表情（サブ計画 4）
- OTA 更新、Wi-Fi、複数端末の同時接続
- 電源電圧の計測（E17 配線に電圧検出が無い。Status の電圧欄は 0 固定で予約）
- Just Works ボンディングを超える認証（MITM 保護、パスキー）
- サーボの電流・温度の自動計測（T-H1 は人の計測）
- サーボの実位置の検出（位置フィードバックが無い。§4.5 の「起動時の跳ね」の制約はここから来る）

### アンチゴール（技術的に動いても失敗とみなすもの）

- 書き込みやリセットのたびに首が暴れる（位置が分からないことによる 1 回の中立合わせは除く。§4.5）
- 機械リミットに勢いよく当たる、または上限を超える指令で止まる（飽和せずに拒否する）
- 休止中にサーボがジリジリ鳴る、熱くなる
- 定型動作の途中で XIAO が再起動する（ブラウンアウト）
- 電源を入れ直すとキャリブレーションが消える、または古い値と新しい値が混ざる
- アプリが切れたのに首が動いたまま、または通電したまま放置される
- キープアライブだけで安全復帰が解除され、古い動作が再開する

## 3. 前提と制約

### 3.1 ハードウェア（確定、E17 配線図と Seeed 公式 wiki で裏取り）

| 項目 | 値 | 根拠 |
|---|---|---|
| ヨー（左右）サーボ信号 | XIAO **D1 = GPIO3**、200 Ω 直列（R1）、47 kΩ プルダウン（R3） | 【利用者】配線、E17 裏面、Seeed wiki のピン表 |
| ピッチ（上下）サーボ信号 | XIAO **D3 = GPIO5**、200 Ω 直列（R2）、47 kΩ プルダウン（R4） | 同上 |
| ストラッピングピン | GPIO2/8/9（D0/D8/D9）。GPIO3/5 は該当しない | Seeed wiki |
| XIAO の給電 | 降圧基板の 5 V → F3（1 A）→ D1（1N4007、帯は 5V ピン側）→ XIAO 5V ピン | E17 裏面 |
| サーボの給電 | 降圧基板の 5 V から直接（上下コネクタ 行 4、左右コネクタ 行 1。N=信号、O=+5 V、P=GND） | E17 |
| 19 V 入力 | DC ジャック + に F1（4 A）。F2 は E17 に無い | E17 |
| 470 µF コンデンサ | 要件定義書 §4.3 に記載があるが E17 には描かれていない | 未確認項目として残す（§7） |
| サーボ | DSSERVO DS3218 相当 ×2、出力軸がジョイント軸と直結（1:1）。DS3218 系はパルス幅 500〜2500 µs（中立 1500 µs）で、動作角 180° と 270° の 2 仕様が販売されている。【利用者】**本機は 180° 仕様**（購入記録） | 要件定義書 §4.1、販売者掲載値（§9）、利用者 |
| 可動域（ジョイント） | ヨー −60°〜+60°、ピッチ −30°〜+30°、正面正対を 0° | 要件定義書 §4.1 |
| 頭部可動部の質量 | 約 523 g（ピッチ）、約 680 g（ヨー） | 要件定義書 §4.2（推定） |
| 無通電時の保持 | 【利用者】ある程度の保持力があり、頭は垂れない | 利用者の実機確認 |
| 信号停止時の挙動 | 【利用者】19 V 給電・PWM なし（AC5 の出力停止状態）で頭は手で回せ、唸らない。一度パルスを受けた後に止めた場合も同じかは新ファームで確認（T-FW-0） | 利用者の実機確認、§7 R9 |

D1（1N4007）により USB の VBUS と 5 V レールは逆流しない。Mac に USB でつないだまま 19 V でサーボを動かす試験構成は成立するはずだが、これは読図からの推定で、実機で確認する（§7 R1）。逆に、USB がつながっている間は 19 V を切っても XIAO は USB から給電され続けて再起動しない。再起動を伴う試験では USB も抜くか RESET を押す（§5 T-FW-4）。

### 3.2 本機の識別

- USB: Espressif「USB JTAG/serial debug unit」（VID 0x303A、PID 0x1001）、Mac では `/dev/cu.usbmodem101`（番号はポートにより変わる）
- USB シリアル番号 = ベース MAC `E0:72:A1:1D:5E:8C`
- ESP32-C3 の Bluetooth アドレスはベース MAC の末尾 +2（Espressif の仕様。既定の universal MAC 数 4 のとき。設定が 2 なら +1）。本機は `INFO` で `addr=e0:72:a1:1d:5e:8e name=CatRobot-5E8E` を確認した（2026-10-23、R3 解消）

### 4.2 アーキテクチャ 【判断】

コア（`lib/catneck`）は入出力を値として受け渡す純粋ロジックで、時計も注入する。プラットフォーム層はその周りの薄いアダプタに限定する。

| 部品 | 役割 | 入出力 |
|---|---|---|
| `Protocol` | バイト列 ⇄ 型付きコマンド／Status／Calibration／Limits／Info の符号化・復号、長さ・範囲の検査 | バイト列 → `Command` または拒否理由。構造体 → バイト列 |
| `Axis`（×2） | ジョイント角の飽和、キャリブレーション（オフセット・反転）でサーボ角へ変換、ゲインで µs へ変換、逆変換（Status 用） | ジョイント角 → サーボ角 → µs |
| `Planner`（軸ごと） | **サーボ角空間**での S 字追従（§4.3）。いつでも目標を差し替えられる | 目標サーボ角・速度上限・tick → 指令サーボ角 |
| `Gesture` | 定型動作の波形生成（§4.4）。上限超過時の時間引き伸ばし | id・振幅・回数・速度 → 時刻ごとの 2 軸ジョイント目標 |
| `Supervisor` | 安全状態機械（§4.5）。通信・切断・STOP・起動猶予・待機を仮想時計で扱う | イベント（コマンド、接続、切断、tick、保存結果）→ 出力（PWM 許可、各軸目標、保存要求、Status） |
| `SerialParser` | テキスト行 → `Command`（§4.7） | 行 → `Command` または応答文 |
| アダプタ | `BleTransport`（NimBLE サーバ）、`SerialTransport`（USB CDC）、`ServoDriver`（ESP32Servo）、`Storage`（Preferences。成功／失敗を返す）、`Clock`（`millis`） | コアの入出力をハードに接続 |

実行モデル: 単一の `loop()` で 20 ms（50 Hz）の tick を回し、BLE の書き込みコールバックはコマンドをキューに積むだけにする（NimBLE のタスクからサーボやコアの状態を直接触らない）。Status 通知は tick から送る。【作り手】FreeRTOS タスクに分けるかは任せるが、コアへの呼び出しは単一スレッドからに限る。

### 4.3 動作仕様（角度・制限・軌道） 【判断】

#### 角度とキャリブレーション

- 角度の約束: ジョイント角で表す。正面正対が 0°。ヨー + はロボット自身の左向き（上から見て反時計回り）、ピッチ + は上向き。反転フラグはこの約束と実機のサーボの向きを合わせるためにある
- 変換の順: 指令ジョイント角 → 角度上限で飽和 → 中立オフセットを加算 → 反転 → **サーボ角目標** → Planner（S 字）→ 指令サーボ角 → パルス幅 = 1500 µs + 指令サーボ角 × ゲイン → 500〜2500 µs で飽和
- Planner がサーボ角空間で動くので、オフセット・反転・角度上限の変更はすべて「サーボ角目標の変更」になり、PWM が飛ばずに S 字で移る。Status の角度は指令サーボ角を逆変換したジョイント角
- ゲイン（µs/°）: DS3218 系は 500〜2500 µs で動作角 180°（11.11 µs/°）と 270°（7.41 µs/°）の 2 仕様がある。【利用者】本機は 180° 仕様なので **既定は 11.11**。ゲインを実際より大きく見積もると実角が指令より大きく出て機械範囲を超える（270° 機に 11.11 で 30° を指令すると実角 45°）ため、購入記録の読み違いに備えて確定手順は +5° から始める（270° 機でも +5° 指令の実角は 7.5°）
- ゲインの確定手順（§5 T-FW-5。定型動作の試験より前に行う）: (1) ピッチ 0° を指令し、頭部に載せた iPhone の「計測」アプリの水準器の読み θ0 を記録する（取付角と中立オフセットの基準）。(2) 低速で +5° を指令し読み θ5 を記録。差分 Δ = θ5 − θ0 の符号が負なら反転フラグを立てて (1) からやり直す。(3) +15°、+30° で同様に差分を取り、ゲイン = 現在のゲイン × 指令角 / Δ を計算する。CENTER で中立に戻してから `GAIN` で保存する（静止・中立でないと拒否される）。(4) 保存後に +30° を再指令し差分が 30° ± 1° であることを確認する。(5) ヨーは同じ型でも独立に確かめる。机に置いた分度器か、iPhone のコンパスの方位差（±3° 程度の誤差）で 0° と +30° の差分を読む。順序は「中立 → 回転方向 → ゲイン」で、反転とオフセットの校正はゲインとは別に行う
- `GAIN` の受理範囲: 5.00〜15.00 µs/°、有限値のみ。範囲外・非数は拒否（`ERR RANGE`）。保守要求（状態を変えない）
- `GAIN` の受理条件: 両軸の Planner が静止している（目標到達済みで速度・加速度 0）こと、かつ再表現後の位置をジョイント角に戻した値が設定上限内であること。満たさなければ適用せず `ERR RANGE`（典型的には「CENTER で中立に戻してから」）。校正手順（下記）は測定後に中立へ戻してから `GAIN` を送る
- `GAIN` 変更時の連続性: ゲインは Planner の後段にあるので、そのまま掛け替えると出力パルスが飛ぶ。受理時は Planner の現在位置を G_old / G_new 倍に再表現してから新ゲインを使う（静止条件により速度・加速度は 0）。これで変更直後の出力パルスは変更前と同じになり、Planner が新ゲインの下でサーボ角目標へ S 字で移る。ホストテストで「変更直後の µs が不変」「静止していないときと範囲外は拒否」を固定する
- 絶対上限（ファームウェアが固定、SET_LIMITS で広げられない）: 角度 ヨー ±60.0°、ピッチ ±30.0°。速度 ヨー 180°/s、ピッチ 120°/s。中立オフセット ±20.0°
- 出荷既定（SET_LIMITS で絶対上限の内側に変更可。保存しない。起動時に既定へ戻る）: 速度 ヨー 120°/s、ピッチ 100°/s。角度 絶対上限と同じ。SET_LIMITS の速度の下限は 5.0°/s、角度上限の下限は 5.0°（1〜49 はそれぞれ 5.0 に飽和、SATURATED）。各欄の 0 は「変更しない」専用で、0° や 0°/s は設定できない。負の角度上限は拒否
- `speed`（MOVE/GESTURE/CENTER の uint8）: 現在の速度上限に対する %（1〜100）。0 は 100 と同じ。100 を超える値は 100 に飽和

#### S 字追従（Planner）の契約

- 周期 50 Hz（20 ms）。各軸の速度上限 V は Limits の値（× speed%）
- 加速度は連続（加加速度制限）。静止から V に達する時間は 0.2 秒以上 0.3 秒以下。ピーク加速度 ≤ 2V / 0.2 s（ヨー既定 1,200°/s²、ピッチ既定 1,000°/s²）、加加速度 ≤ 4V / (0.2 s)²（ヨー既定 12,000°/s³、ピッチ既定 10,000°/s³）。注: 加速度を 0 から連続に立ち上げる以上、平均加速度 V/0.2 s では 0.2 秒で V に届かない。だからピークは平均の 2 倍を許す
- 目標を保持しているとき: 行き過ぎずに到達し、到達時は位置 = 目標、速度 0、加速度 0 の静止状態に着地する（最終 tick の補正量は 0.1° 以下、速度の切り捨ては 0.5°/s 以下）。着地後は目標が変わるまで位置・速度・加速度が不変。既定速度で 60° 移動が 1.0 秒以内
- 目標はどの tick でも差し替えられる。差し替え時に速度・加速度は不連続にならない。Planner は常に「制動点」（今から加速度・加加速度の上限内で減速したときに止まれる位置）を持ち、制動点は**絶対上限**（ヨー ±60°、ピッチ ±30°、機械範囲）内にあることを保証する。目標の差し替えで制動点は遠ざからない（最大減速で縮むことはある）。新目標が制動点より手前に来た場合は、上限内で減速して新目標を通り過ぎてから戻る（通り過ぎは許す）。したがって連続して目標が変わっても、位置は絶対上限を超えない。これは「目標を超えない」より弱いが実現可能な契約で、テストは乱数の連続差し替えで |位置| ≤ 絶対上限 と、差し替えが止まった後の収束を確かめる
- 設定上限（SET_LIMITS の角度上限）は目標の飽和にだけ使う。現在位置より内側に設定上限を下げた場合、目標が再飽和されて Planner が S 字で設定上限内へ戻る。その移行中は位置が設定上限の外にあってよい（絶対上限は常に守る）。移行の完了は目標到達で判定する
- 速度上限を現在速度より下げられた場合（SET_LIMITS、安全復帰速度への切り替え、speed% の変更を含む）は、**旧上限の a_max・j_max を使ったまま**加速度を 0 に戻しつつ減速し、新上限の a_max・j_max に切り替える。【実装での確定（2026-10-23）】切り替え点は「|速度| ≤ 新上限 かつ 加速度 = 0」の特別な場合である**完全停止**とする。新上限まで減速した時点で切り替えると、切替後の小さい a_max・j_max で制動距離が伸びて本節の「制動点は遠ざからない」と矛盾するため。代償は、走行中に上限が下がると一瞬止まってから動き直す見た目。Planner は常に両方向の不変条件「v + max(a, 0)² / (2 j_max) ≤ V」かつ「v − max(−a, 0)² / (2 j_max) ≥ −V」を保つので、旧 j_max で減速する限り移行中も旧上限を超えない。移行時間の上限は T_tr = (V_old − V_new) / a_old + 3 × a_old / j_old。移行中は速度が新上限を超えてよいが、旧上限と絶対上限は超えない。T_tr 経過後は新上限内。上限の引き上げは即時。再生中の GESTURE にも同じ規則を適用する（波形は崩れてよい）。ホストテストはこの移行規則で期待値を作り、「減速しない違反」と「移行中の一時超過」を区別する
- 2 軸の開始ずらし（FW-PWR-1）: 同じ tick で両軸が静止から動き出すとき、ピッチ側の開始を **3 tick（60 ms）** 遅らせる。要件の 50 ms は「50 ms 以上」と解釈し、tick で量子化する
- 上記の数値は【判断】で暫定。§5 の T-FW-2 でブラウンアウトや機械的な衝撃が見えたら、既定速度を下げる（絶対上限は据え置き）。要件定義書 §7.3 の修正案は §8

### 4.4 定型動作（GESTURE） 【判断】

- 起点は中立。現在角が中立でなければ、まず S 字で中立へ移動してから波形を再生する
- 波形は始端（t = 0）と終端（t = T）で位置 0・速度 0・加速度 0 に静止から始まり静止に終わる滑らかな形（C²）とし、途中で極値 ±amp に達する（nod は −amp が先）。関数形（窓つき正弦、5 次多項式の連結など）は作り手に任せる。単純な sin(2πt/T) は始端の速度が 0 でないので使わない
- 【実装での確定（2026-10-23、ledger Task 6）】波形を tick ごとに Planner に追従させる方式は採らない。目標で停止できることを保証する Planner（§4.3 の制動点契約）は動く目標に制動距離ぶん遅れ、nod 15° で 1 往復 1.56 秒・振幅 13.4° となり受入（1.0〜1.3 秒・振幅 90%）を満たさなかった。代わりに**極値を経由する静止→静止の S 字移動の列**として Planner に渡す: nod は 0 → −amp → +amp →（くり返し）→ 0、shake は 0 → +amp → −amp → … → 0、tilt は (±amp, −amp/2) で 1.5 秒保持 → 0、look は (0, ±amp) で 2.0 秒保持 → 0。各区切りは両軸が静止してから次へ進む。振幅は厳密に ±amp、上限・連続性・2 軸ずらし・SET_LIMITS 中の移行規則は Planner がそのまま保証する。所要時間は上限で決まり、既定上限で nod 15° は 1.30 秒、nod 10° は約 1.0 秒。上の「関数形」と下の「基準時間」の表は当初案として残す
- 下記の GesturePlayer（窓つき正弦・5 次多項式の波形、`lib/catneck/Gesture.*`）は Supervisor から使われていない。撤去するか、波形を直接出力して上限低下時だけ Planner へ引き渡す方式で再利用するかは利用者の判断
- 基準時間（`speed` = 100 のとき、当初案）。`speed` の実装: 保持時間（tilt 1.5 秒、look 2.0 秒）を 100/speed 倍に伸ばし、移動区間は Planner の速度上限を speed% に縮める。静止→静止の移動なので移動区間の時間は厳密に 100/speed 倍にならない（nod 15° は speed 50 で約 1.4 倍）

| id | 名称 | 軸と振幅 | 波形と基準時間 |
|---|---|---|---|
| 1 | nod | ピッチ ±amp | 0 → −amp → +amp → 0 を 1 往復 **1.0 秒**【利用者の希望に合わせた値】 |
| 2 | shake | ヨー ±amp | 0 → +amp → −amp → 0 を 1 往復 1.0 秒 |
| 3 | tilt_l | ヨー +amp、ピッチ −amp × 0.5 | 寄せる 0.4 秒、保持 1.5 秒、戻る 0.4 秒 |
| 4 | tilt_r | ヨー −amp、ピッチ −amp × 0.5 | 同上 |
| 5 | look_up | ピッチ +amp | 移動 1.0 秒、保持 2.0 秒、戻る 1.0 秒 |
| 6 | look_down | ピッチ −amp | 同上 |

- `amp` は 0.1° 単位の uint8（最大 25.5°）。角度上限で飽和する
- `repeats` は 1〜3（0 は 1、4 以上は 3）。全 id で「1 サイクル」を回数分くり返す
- 波形の最大速度・最大加速度・最大加加速度が Planner の上限（V、a_max、j_max）を超える場合は、振幅を保って時間を伸ばす（三つとも上限内に収まる最小の伸び率 = max(1, v/V, √(a/a_max), ∛(j/j_max))）。それでも Planner は安全網として働くので、結合試験（§4.10 5）で nod large の実出力が振幅 ≥ 90%・1 往復 1.0〜1.3 秒・終端静止を満たすことを確かめる
- 競合: GESTURE 再生中に届いた MOVE/CENTER は「最新の目標」として 1 件だけ保持し、GESTURE（保留分を含む）完了後に適用する。GESTURE 再生中の GESTURE は保留 1 件（新しいものが古い保留を置き換える）。STOP／TORQUE 0 と安全復帰（§4.5）は再生中・保留中のすべてを破棄する
- 付録 B の `look_at_user` と `center` は GESTURE ではなくアプリ側が MOVE/CENTER で行う（要件定義書どおり）

### 4.5 安全状態機械（Supervisor） 【判断】

#### イベントの分類

| 分類 | 含まれるもの | 効果 |
|---|---|---|
| 動作要求 | MOVE、GESTURE、CENTER、TORQUE 1、SET_CAL、Calibration 特性への Write | 通信あり。IDLE／RETURNING／RELAX_WAIT を ACTIVE へ戻す |
| 保守要求 | PING、SET_LIMITS、Limits 特性への Write、SAVE_CAL、シリアルの `GAIN`・`SAVE` | 通信あり。状態は変えない（RETURNING／RELAX_WAIT を解除しない）。BOOT 中は破棄 |
| 停止要求 | STOP、TORQUE 0 | どの状態からも最優先で IDLE へ（BOOT 中は記憶して BOOT_CENTER を抑止）。再生中・保留中の動作をすべて破棄 |
| 読み取り | Status/Calibration/Limits/Info の Read、シリアルの `STATUS`/`WATCH`/`INFO`/`HELP` | 通信に数えない |
| 拒否された入力 | §4.6 の拒否条件に当たるもの | 通信に数えない。REJECTED を立てる |
| リンク | BLE 接続・切断 | 切断は ACTIVE から RETURNING へ |

#### 状態

時間の数値はすべてコアの定数とし、テストで固定する。時間の原点は電源投入（`setup()` 開始）。

| 状態 | PWM | 入ったときの動作 | 出る条件 |
|---|---|---|---|
| BOOT | 停止 | 電源投入から **500 ms** は何も出力しない（FW-PWR-2）。この間に届いた動作要求・保守要求は破棄する（REJECTED は立てない。通信にも数えない）。停止要求だけは記憶する | 500 ms 経過 → 停止要求を受けていれば IDLE（BOOT_CENTER の出力を抑止）、そうでなければ BOOT_CENTER |
| BOOT_CENTER | 出力 | サーボを接続し中立（キャリブレーション後）を出力（FW-SAFE-3） | 電源投入から **1.5 秒**（= 500 ms + 1.0 秒）までに動作要求なし → IDLE。動作要求あり → ACTIVE |
| IDLE | 停止 | サーボを切り離す（プルダウンで信号は L）。アドバタイズは継続 | 動作要求 → ACTIVE |
| ACTIVE | 出力 | 補間を回す。最後の通信からの時間を数える | 通信（動作要求・保守要求）が **3.0 秒** 届かない → RETURNING。BLE 切断 → RETURNING（待たない）。停止要求 → IDLE |
| RETURNING | 出力 | 再生中・保留中の動作をすべて破棄し、**安全復帰速度（ヨー 90°/s、ピッチ 60°/s。Limits と無関係の定数）**で中立へ S 字移動 | 中立到達、または開始から **2.0 秒** 経過（期限）→ RELAX_WAIT。動作要求 → ACTIVE。停止要求 → IDLE |
| RELAX_WAIT | 出力 | 中立（または期限時の位置）を **2.0 秒** 保持 | 経過 → IDLE。動作要求 → ACTIVE。停止要求 → IDLE |

- 最悪の脱力時刻: 切断検出から 2.0 + 2.0 = 4.0 秒。無通信なら最後の通信から 3.0 + 4.0 = 7.0 秒。T-LINK-1 の修正案（§8）はこれに合わせて「切断検出から 5 秒以内」
- 位置検出が無いことによる制約: BOOT_CENTER の最初のパルスと、IDLE → ACTIVE の最初のパルスでは、サーボが「最後の指令角（または中立）」と実位置の差を自分の速度で詰める。普段は安全復帰で中立に戻ってから脱力するので差は小さいが、動作中の電源断や手で頭を動かした後は 1 回の速い合わせ動作が起きる。これは解消できない仕様として記録し、T-FW-1 の合格条件は「中立付近で電源を切った後の起動で目に見える跳ねがない」に限定する。サブ計画 3 は接続直後に低速の CENTER を送ることを推奨するが、最初のパルスの合わせ動作はそれでも防げない
- 切断後に再接続しても、状態機械は ACTIVE へ戻らない。アプリの動作要求で戻る
- 接続したまま通信が続く間は ACTIVE のまま通電を保持する（ファームウェアは自動で脱力しない）。長く動かさないときに脱力させるのはアプリの責務で、TORQUE 0 を送る（サブ計画 3 への契約。T-H1 の「±30° で 10 分保持」が通電保持の前提）。自動脱力を入れると再通電のたびに合わせ動作（R7）が起きるため採用しない
- ブラウンアウト: 起動時のリセット理由がブラウンアウトなら Status の BROWNOUT を立て、次の正常起動まで保持。アドバタイズは起動処理で必ず再開する（FW-SAFE-5）
- 要件定義書 FW-SAFE-1/2 と T-LINK-1 の時間の食い違い（codex 指摘）は、上の表の値で統一し、§8 で修正案を出す

### 4.6 BLE GATT プロトコル版 1 【判断】

#### アドバタイズと接続

- 名前 `CatRobot-XXXX`。XXXX は Bluetooth アドレス末尾 2 バイトの大文字 16 進（本機の見込みは `CatRobot-5E8E`）。スキャン応答にサービス UUID（128 bit）を載せる
- 接続間隔は 15〜30 ms を要求（12〜24 単位）。1 台の central のみ。接続中はアドバタイズを止める
- セキュリティ: Just Works ボンディング（bond = 有効、MITM = 無効、Secure Connections = 有効）。Info 以外の特性は暗号化リンクでのみ読み書き・通知できる
- ペアリング窓: ボンド済み端末が 1 台も無ければ常時受け付ける。1 台以上あれば、電源投入後 **60 秒** とシリアルの `PAIR OPEN` 後 60 秒だけ新規ペアリングを受け付け、それ以外は未ボンドの central を接続直後に切断する。ボンドはシリアルの `BONDS CLEAR` で全消去
- 【作り手】窓の実装方法（接続コールバックでの切断、または白リスト）は NimBLE の挙動を実機で確かめて選ぶ。iOS は解決可能プライベートアドレスを使うので、ボンド済み判定はアドレス解決に依存する（§7 R2）

#### サービスと特性

サービス UUID `C47B0000-6D1F-4B9E-9C9A-2A3B4C5D6E7F`。特性はベースの 16 bit 部分を置き換える。多バイトはすべてリトルエンディアン、角度は 0.1° 単位 int16、速度は 0.1°/s 単位 uint16。

| 特性 | UUID | 属性 | 長さ | 内容 |
|---|---|---|---|---|
| Command | `C47B0001-…` | Write Without Response（暗号化必須） | 1〜20 B | 下表のコマンド |
| Status | `C47B0002-…` | Notify、Read（暗号化必須） | 12 B | 下記 |
| Calibration | `C47B0003-…` | Read / Write（暗号化必須） | 6 B | 下記。Write は SET_CAL と同じ（一時適用、動作要求） |
| Limits | `C47B0004-…` | Read / Write（暗号化必須） | 8 B | 下記。Write は SET_LIMITS と同じ |
| Info | `C47B0005-…` | Read（暗号化不要） | 8 B | 下記 |

Status（12 B）:

| オフセット | 型 | 内容 |
|---|---|---|
| 0 | int16 | ヨー指令角（0.1°）。サーボに位置検出が無いため、補間中の指令角であって実測角ではない |
| 2 | int16 | ピッチ指令角（0.1°） |
| 4 | uint16 | フラグ: bit0 LINK（central 接続中）、bit1 TORQUE（PWM 出力中）、bit2 MOVING（目標未到達）、bit3 BROWNOUT、bit4 SATURATED（直近の受理コマンドを飽和させた）、bit5 CAL_DIRTY（適用中のキャリブレーションが保存値と異なる）、bit6 GESTURE（再生中または保留あり）、bit7 REJECTED（直近のコマンドを拒否。次の受理で下げる）、bit8 RETURNING（安全復帰中または待機中）、bit9 PAIR_OPEN（新規ペアリング受付中）、bit10 SAVE_ERROR（`save_seq` の SAVE_CAL が失敗。次の SAVE_CAL の処理完了時に `save_seq` と一組で更新し、他のコマンドでは変えない）。他は 0 |
| 6 | uint8 | 最後に受理した PING の seq |
| 7 | uint8 | 状態: 0 BOOT、1 BOOT_CENTER、2 IDLE、3 ACTIVE、4 RETURNING、5 RELAX_WAIT |
| 8 | uint16 | 電源電圧（0.01 V）。本ハードでは計測できないため 0 |
| 10 | uint8 | 起動後に拒否したコマンドの累計（255 で止める） |
| 11 | uint8 | `save_seq`: 最後に処理した SAVE_CAL の `req`（起動後に未処理なら 0）。SAVE_ERROR はこの `req` の保存結果を表す |

通知: 接続中は 200 ms ごと（5 Hz）。seq・フラグ・状態・`save_seq` が変わったときは次の tick（≤ 20 ms）で追加通知。

Calibration（6 B）: ヨーオフセット int16（0.1°）、ピッチオフセット int16、反転 uint8（bit0 ヨー、bit1 ピッチ）、saved uint8（Read: 適用中の値が保存値と一致なら 1。Write: 無視）。

Limits（8 B）: ヨー速度上限 uint16（0.1°/s）、ピッチ速度上限 uint16、ヨー角度上限 int16（0.1°、対称な絶対値）、ピッチ角度上限 int16。Read は適用中の値。

Info（8 B）: プロトコル版 uint8（= 1）、ファームウェア版 major/minor/patch 各 uint8（初版 0.1.0）、ハードウェア ID uint8（= 1、E17 配線）、能力 uint8（bit0 電圧計測あり = 0）、予約 uint16（0）。

#### コマンド（先頭 1 バイトが種別、長さは固定）

| 種別 | 名称 | 長さ | ペイロード | 動作 |
|---|---|---|---|---|
| 0x01 | MOVE | 6 | yaw int16、pitch int16、speed uint8 | 両軸の目標を差し替え。設定上限で飽和（SATURATED） |
| 0x02 | GESTURE | 5 | id uint8（1〜6）、amp uint8（0.1°）、repeats uint8、speed uint8 | §4.4 |
| 0x03 | STOP | 1 | なし | 補間と保留を破棄し即時脱力（IDLE） |
| 0x04 | CENTER | 2 | speed uint8 | 目標 (0, 0) へ移動。GESTURE 中は完了後 |
| 0x05 | TORQUE | 2 | on uint8（0/1） | 0: IDLE へ。1: 現在の指令角で出力開始（ACTIVE） |
| 0x06 | SET_CAL | 6 | yaw_off int16、pitch_off int16、invert uint8 | 一時適用。どの状態でも受理し、動作要求として ACTIVE へ（IDLE なら出力を開始）。変更は Planner を通して S 字で反映。オフセットは ±20.0° で飽和、invert は bit0/1 以外を無視。SAVE_ERROR と `save_seq` は変えない |
| 0x07 | SAVE_CAL | 2 | req uint8（1〜255。0 は拒否） | 適用中の値を NVS に保存。保存値が既に同じなら書き込みを省略して成功扱い。成功（書き込み後の読み戻しが一致）で CAL_DIRTY と SAVE_ERROR を下げ、失敗で SAVE_ERROR を立てる。処理後に `save_seq` = req とし、変化による即時 Status 通知で結果を伝える。同じ req の再送は同じ処理を繰り返す（冪等）。保守要求 |
| 0x08 | SET_LIMITS | 9 | yaw_v uint16、pitch_v uint16、yaw_a int16、pitch_a int16 | 絶対上限の内側、下限 5.0°/s・5.0° に飽和して更新。各欄 0 は「変更しない」。即時に有効で、角度上限は現在の目標の再飽和としてサーボ角目標に反映（S 字で移る）、速度上限は §4.3 の減速規則で反映。保守要求 |
| 0x09 | PING | 2 | seq uint8 | キープアライブ。Status の seq に反映。保守要求 |

- 拒否（無視して REJECTED を立て、累計に加える。通信に数えない）: 長さ不一致、未知の種別、GESTURE の id が 1〜6 以外、TORQUE の on が 0/1 以外、SET_LIMITS の角度上限が負、SAVE_CAL の req が 0
- 拒否以外の範囲外は飽和して受理し SATURATED を立てる
- MOVE は 50 Hz まで連続受信できる。同じ tick に複数届いたら最後の値を使う
- クライアントへの指針（サブ計画 3 向け）: Command は Write Without Response なので BLE 層の到達確認はない。校正の保存は次の手順で確かめる。(1) 保存したい値を SET_CAL で送る（プレビューは何度送ってもよい）。(2) 直前の Status の `save_seq` と異なる `req`（1〜255）を選び SAVE_CAL(req) を送る。(3) `save_seq` = req の Status を待つ。SAVE_ERROR = 0 なら保存成功、1 なら失敗。1 秒以内に来なければ同じ req で再送する（冪等）。(4) 成功後に Calibration を Read し、`saved` = 1 かつ値が意図どおりかを照合する。違えば（途中の SET_CAL が落ちた場合）SET_CAL から新しい req でやり直す。シリアルの `CAL`／`GAIN` も同じ校正状態を変えるが、`save_seq` は SAVE_CAL/`SAVE` 以外では変わらない

### 4.7 シリアル経路（NFR-MAINT-2） 【判断】

- USB CDC（`Serial`）、行単位のテキスト。改行は LF（CR は無視）。大文字小文字を区別しない。応答は `OK …` または `ERR <理由>`。角度・速度の引数は度（小数可）
- コマンドはコアの同じ `Command` に変換して Supervisor に渡す。したがって BLE と挙動が一致する。通信扱い（ウォッチドッグの更新）と動作要求／保守要求の分類も BLE と同じ

| 行 | 動作 |
|---|---|
| `MOVE <yaw> <pitch> [speed]` | MOVE |
| `GESTURE <id または名称> <amp> [repeats] [speed]` | GESTURE |
| `STOP` / `CENTER [speed]` / `TORQUE 0\|1` / `PING [seq]` | 同名のコマンド |
| `CAL <yaw_off> <pitch_off> <invert>` / `SAVE [req]` | SET_CAL / SAVE_CAL（req 省略時は前回 +1。応答は保存結果を待ってから `OK seq=<req>` または `ERR SAVE`） |
| `LIMITS <yaw_v> <pitch_v> <yaw_a> <pitch_a>` | SET_LIMITS（0 は変更しない） |
| `GAIN <yaw_us_per_deg> <pitch_us_per_deg>` | サーボゲインを設定し保存（BLE には無い。§4.3 の範囲外は `ERR RANGE`） |
| `HEX <16 進バイト列>` | 生のプロトコルバイト列を BLE と同じ復号器に通す（経路の同一性の確認用） |
| `STATUS` / `WATCH ON\|OFF` | Status を 1 行で表示 / 5 Hz で流し続ける |
| `INFO` | 版数、プロトコル版、ハード ID、Bluetooth アドレスと名前、ボンド数、ペアリング窓の状態、リセット理由 |
| `BONDS CLEAR` / `PAIR OPEN` | ボンド全消去 / ペアリング窓を 60 秒開く |
| `HELP` | 一覧 |

起動時に 1 行 `CATNECK fw=0.1.0 proto=1 hw=E17 reset=<理由> brownout=0|1` を出す。他のログは既定で出さない（`WATCH` で見る）。

### 4.8 永続化 【判断】

- Preferences の名前空間 `catneck`、キーは **1 つ**（`cal`）。値は固定長の構造体 1 件: スキーマ版 uint8（= 1）、ヨー／ピッチオフセット int16、反転 uint8、ヨー／ピッチゲイン uint16（0.01 µs/°）、CRC16。1 キーに丸ごと書くので、途中で電源が落ちても旧一式か新一式のどちらかしか残らない
- 書き込みは SAVE_CAL と GAIN のときだけ（NVS の摩耗を避ける）。書き込み後に読み戻して一致を確認し、一致したときだけ成功とする。Limits は保存しない
- 読めない・CRC 不一致・版が違うときは既定値（オフセット 0、反転なし、ゲイン 11.11）で起動し、CAL_DIRTY を立てる
- `Storage` アダプタは成功／失敗を返すインターフェースとし、ホストテストで失敗を注入できるようにする

### 4.9 Mac 用の試験ツール 【判断】

- `tools/ble_client.py`（bleak）: `scan`、`info`、`watch`（Status を表示）、`move`、`gesture`、`stop`、`center`、`torque`、`cal get|set|save`（save は CAL_DIRTY/SAVE_ERROR で結果を表示）、`limits get|set`、`keepalive`（1 Hz の PING を送り続ける）、`demo`（6 種 × small/medium/large を順に再生）、`latency`（Command 書き込みから MOVING=1 の Status 受信までを計る）、`reconnect`（切断→再接続の所要時間）
- `tools/serial_cli.py`（pyserial）: 行を送って応答を表示、`WATCH ON` の流し読み
- macOS の注意: 機器の識別子は MAC ではなく UUID。暗号化特性への最初のアクセスで OS がペアリングを始める（ダイアログが出ることがある）。bleak の macOS バックエンドでは `pair()` は未実装（NotImplementedError）で、`pair=True` は無視される。再ペアリング試験の前には Mac 側の Bluetooth 設定から本機を削除し、本機側は `BONDS CLEAR`
- Python 依存の固定: ファイル冒頭の PEP 723 ブロックに `bleak==3.0.2`、`pyserial==3.5`。`uv run tools/ble_client.py …` で実行

### 4.10 テスト戦略 【判断】

ホスト単体テスト（Unity、`pio test -e native`、ネットワーク・実機不要）。最低限:

1. `Protocol`: 全コマンドの復号（境界値、長さ違い、未知種別、拒否理由）、Status/Calibration/Limits/Info の符号化（固定長・オフセット・エンディアン・フラグのビット位置）
2. `Axis`: 飽和、オフセットと反転の適用順、ゲインと逆変換、500〜2500 µs の飽和、絶対上限を SET_LIMITS で広げられないこと、速度の下限 5.0°/s、`GAIN` の受理範囲
3. `Planner`: 毎 tick の速度・加速度・加加速度が §4.3 の上限内（速度上限の引き下げ時は移行規則で判定）、静止→V の所要時間が 0.2〜0.3 秒、保持目標で行き過ぎなし・到達、既定速度で 60° が 1.0 秒以内、目標差し替え時の連続性、乱数の連続差し替えで |位置| ≤ 絶対上限 と収束、設定上限を現在位置より内側へ下げたときの S 字復帰、加速度が最大のときに速度上限を下げても旧上限を超えないこと（旧 j_max での減速）、T_tr 後の新上限遵守
4. `Gesture`: 6 種の波形の時間・振幅、上限超過時の引き伸ばし率、repeats、保留と競合の規則、再生中の SET_LIMITS で移行規則に従うこと
5. `Supervisor`: 状態 × イベントの表を網羅（RETURNING と RELAX_WAIT のそれぞれで保守要求が復帰を解除しないこと、TORQUE 0 が再生中と保留中の両方を破棄すること、GESTURE 再生中の SET_LIMITS が移行規則に従うこと、nod large の結合試験を含む）。仮想時計で BOOT の 500 ms 無出力、BOOT 中の要求破棄と停止要求による BOOT_CENTER 抑止、`save_seq` と SAVE_CAL の冪等性（同じ req の再送、req 0 の拒否）、`GAIN` の受理条件（静止・範囲内のみ。移動中と範囲外は拒否し µs 不変）、電源投入から 1.5 秒で IDLE、無通信 3 秒 → RETURNING → 中立 → 2 秒 → IDLE、復帰の 2 秒期限、切断の即時復帰、RETURNING/RELAX_WAIT 中の PING・SAVE_CAL・SET_LIMITS が復帰を解除しないこと、STOP/TORQUE 0 の最優先、拒否入力がウォッチドッグを更新しないこと、再接続後に勝手に動かないこと、2 軸 3 tick ずらし、SAVE_CAL の成功／失敗注入と CAL_DIRTY/SAVE_ERROR、BROWNOUT・REJECTED・SATURATED のフラグ
6. `SerialParser`: 各行の解釈、`HEX` が BLE 復号と同じ `Command` になること、`SAVE` の応答が保存結果に従うこと

実機受入は §5。

## 5. 受入基準（「できた」の定義）

実機（19 V 給電、首組み立て済み）で以下を満たす。T-FW-2〜4 が【利用者】の「各種そぶりができる」に当たる。

| ID | 内容 | 合格 |
|---|---|---|
| T-FW-0 | 脱力の確認 | 19 V 給電で PWM を出した後に止め（`TORQUE 0`）、頭が手で回せて唸らないこと。保持し続ける場合は §7 R9 の分岐へ |
| T-FW-1 | 起動 | 中立付近で電源を切った後、19 V 投入・リセットのいずれでも目に見える跳ねがない。起動行が出る。電源投入から 1.5 秒以内に脱力（IDLE）。動作中の電源断からの起動は「1 回の合わせ動作のみ」で、その後は静止 |
| T-FW-2 | 定型動作 | `ble_client.py demo` で 6 種 × 3 段階が目で分かる形で再生される。頷き large の 1 往復は 1.0〜1.3 秒。BROWNOUT が立たず、XIAO が再起動しない。USB を同時接続していても切れない |
| T-FW-3 | 安全復帰 | キープアライブを止めて 3 秒以内に復帰が始まり、中立で 2 秒後に脱力。クライアントを強制終了（切断）すると待たずに復帰。切断検出から 5 秒以内に脱力。復帰中に PING を送っても復帰が続く |
| T-FW-4 | キャリブレーション | `cal set` → 首が追従（IDLE からでも出力が始まる）→ `cal save`（`save_seq` の一致と SAVE_ERROR = 0、Calibration Read の照合）→ 19 V と USB の両方を切って入れ直す（起動行の reset 理由で再起動を確認）→ `cal get` が同じ値、中立が同じ向き |
| T-FW-5 | 制限とゲイン（T-FW-2 より先に実施） | §4.3 の手順どおり、0° の読みを基準に +5°/+15°/+30° の差分角で回転方向とゲインを確かめ、必要なら `GAIN` で補正。補正後に +30° の差分が 30° ± 1°。ヨーも差分角で独立に確認。そのうえで ±60°/±30° の指令で機械リミットに当たらないことを確認。絶対上限を超える `limits set` は内側に飽和、5°/s・5° 未満は下限に飽和 |
| T-FW-6 | 遅延 | Command 書き込みから MOVING=1 の Status まで 10 回の中央値 300 ms 以下（NFR-PERF-3 の代理指標。首の物理的な動き出しは含まない） |
| T-FW-7 | 再接続 | 切断から再接続完了まで 5 秒以内（NFR-REL-2） |
| T-FW-8 | シリアル同等性 | `serial_cli.py` から同じ定型動作ができる。`HEX` の結果が BLE と一致 |
| T-FW-9 | ペアリング | Mac とボンドできる。`BONDS CLEAR` 後に再ペアリングできる。窓が閉じた後に未ボンド端末が接続を保てないことは、二台目の端末（iPhone の汎用 BLE アプリなど）があれば確認し、無ければ未実施と記録 |
| T-FW-10 | ホストテスト | `pio test -e native` が全件合格。実機・ネットワーク不要 |

T-H1〜H3（保持電流・温度、緩み、質量）は要件定義書どおり人の計測で、本サブ計画の合否には含めない。
